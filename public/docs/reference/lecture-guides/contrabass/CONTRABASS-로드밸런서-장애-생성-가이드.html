CONTRABASS 로드밸런서

PENDING_CREATE 장애 원인·조치 및 생성 가이드

*본 문서에서 다루는 내용은 아카데미 CONTRABASS에 생성된 자원을 기준으로 작성되었습니다.

항목내용
대상 환경교육센터 CONTRABASS v3.0.6 (edu306), OpenStack Octavia (amphora 드라이버)
작성일2026-10-30
작성자최우성 (교육팀)
요약컨트롤러 2대(rack6-1-con1, rack6-2-con2)의 o-hm0 인터페이스에 관리망 IP가 없어 Octavia worker가 amphora에 접속하지 못함 → 로드밸런서가 PENDING_CREATE에서 멈춤. octavia-interface 서비스 재기동으로 해결.

요약

한 줄 요약컨트롤러 2대의 o-hm0 인터페이스에서 관리망 IP가 빠져 Octavia가 amphora에 접속하지 못했고, 그래서 로드밸런서가 PENDING_CREATE에서 멈췄다. 각 컨트롤러에서 systemctl start octavia-interface로 IP를 복구해 해결했다.
구분내용
증상로드밸런서 생성 후 PENDING_CREATE / OFFLINE 상태에서 멈춤. ERROR로도 바뀌지 않고 포털에서 삭제도 되지 않음
영향 범위세그먼트와 관계없이 모든 신규 로드밸런서 (2026-10-30 테스트 3개, 2026-10-01 생성된 lb-01)
원인rack6-1-con1, rack6-2-con2의 o-hm0에 lb-mgmt-net IP(198.18.0.2, 198.18.0.3)가 없음 → 이 노드의 Octavia worker가 amphora 9443/tcp에 접속 실패
해결두 컨트롤러에서 systemctl start octavia-interface 실행 → o-hm0 IP와 198.18.0.0/22 경로 복구
검증조치 후 새로 만든 test-lb-verify가 약 2분 만에 ACTIVE / ONLINE
정리멈춘 로드밸런서 4개는 DB에서 상태를 ERROR로 바꾼 뒤 포털에서 삭제
후속 조치o-hm0 IP 주기 점검 장치 추가, 컨트롤러 Swap 사용률(96~100%) 점검, 남은 보안 그룹 정리 (라이프사이클팀 검토)

빠른 점검법: 로드밸런서가 5분 넘게 PENDING_CREATE이면, 컨트롤러 3대에서 아래 명령으로 o-hm0에 172.16.0.x 주소가 있는지 먼저 확인하세요.

ip -br addr show o-hm0; systemctl is-active octavia-interface

1. 로드밸런서 생성 시 PENDING_CREATE 오류의 원인

1.1 현상

구분내용
발생 증상로드밸런서 생성 후 프로비저닝 상태가 PENDING_CREATE, 오퍼레이팅 상태가 OFFLINE에서 변하지 않음. 시간이 지나도 ERROR로도 바뀌지 않음
재현 범위세그먼트 3개(198.51.100.0/24, 203.0.113.0/24, yj-test-18-network) 모두 동일 → 세그먼트 문제 아님
과거 사례academy 프로젝트 lb-01이 2026-10-01부터 같은 상태로 남아 있었음
포털 영향PENDING_* 상태에서는 Octavia가 삭제를 거부하므로 포털에서 삭제해도 반응 없음

1.2 Octavia 로드밸런서 생성 흐름

로드밸런서 1개를 만들면 Octavia worker가 아래 순서로 작업합니다. 이번 장애는 ④ 단계에서 멈췄습니다.

  1. VIP 포트와 VIP 보안 그룹(lb-<LB ID>) 생성 (service 프로젝트)
  2. amphora VM 2대 생성 (ACTIVE_STANDBY, anti-affinity로 서로 다른 호스트에 배치)
  3. amphora VM 부팅, amphora-agent가 9443/tcp로 대기
  4. 컨트롤러 → amphora 9443/tcp 접속 확인 ← 이번 장애 지점
  5. amphora에 VIP 네트워크 인터페이스 연결, 리스너 설정 전달
  6. 프로비저닝 상태 ACTIVE로 변경

1.3 근본 원인: 컨트롤러의 o-hm0 인터페이스 IP 누락

Octavia worker와 health manager는 컨트롤러 서버에서 일반 프로세스로 실행되고, amphora VM은 OpenStack 가상 네트워크인 lb-mgmt-net(198.18.0.0/22) 안에 있습니다. 컨트롤러가 이 가상 네트워크와 통신하려면 OVS br-int에 연결된 o-hm0 인터페이스가 관리망 IP를 가지고 있어야 합니다.

[컨트롤러]                                  [컴퓨트 노드]
octavia-worker ──┐                          amphora VM
health-manager ──┤                          (172.16.x.x)
                 o-hm0 (172.16.0.x) ── OVS br-int ── lb-mgmt-net ──┘

o-hm0은 octavia-interface 서비스(/usr/local/bin/octavia-interface.sh)가 부팅 시 한 번 만들어 고정 IP를 넣습니다. 장애 시점 컨트롤러별 상태는 다음과 같았습니다.

컨트롤러o-hm0 IPv4octavia-interface영향
rack6-1-con1없음 (IPv6 링크로컬만)inactive (dead)이 노드 worker가 맡은 작업 실패
rack6-2-con2없음 (IPv6 링크로컬만)inactive (dead)test-lb-yj18 생성 실패 (로그 확인)
rack6-3-con3198.18.0.4/22 정상active정상

Octavia는 생성 요청을 3대의 worker 중 하나에 배정합니다. o-hm0이 고장 난 노드에 배정되면 amphora에 접속하지 못해 실패하고, 실패 후에도 상태를 ERROR로 바꾸지 못한 채 PENDING_CREATE로 남았습니다.

1.4 근거 로그

rack6-2-con2의 /var/log/octavia/octavia-worker.log (2026-10-30 13:15):

ERROR oslo_messaging.rpc.server taskflow.exceptions.WrappedFailure:
  ComputeWaitTimeoutException: Waiting for compute id ... to go active timeout.
  AmpConnectionRetry: Could not connect to amphora ...
  HTTPSConnectionPool(host='198.18.1.149', port=9443): Max retries exceeded
  (Caused by ConnectTimeoutError(... 'Connection to 198.18.1.149 timed out.'))

컨트롤러에서 직접 접속 테스트를 했을 때도 같은 결과였습니다.

$ curl -vk --connect-timeout 5 https://198.18.0.242:9443/
* Failed to connect to 198.18.0.242 port 9443 after 5002 ms: Timeout was reached

IP가 없어진 정확한 시점과 이유는 확인하지 못했습니다. 서버는 2026-05-29 이후 재부팅이 없었으므로, 부팅 실패가 아니라 그 이후 누군가 stop을 실행했거나 IP가 지워진 것으로 추정됩니다.

2. 해결 방법

주의공용 교육 환경의 컨트롤러 설정을 바꾸는 작업입니다. 실행 전에 라이프사이클팀과 협의하세요. 명령은 각 컨트롤러에 root로 접속해 실행합니다.

2.1 진단

각 컨트롤러(rack6-1-con1 192.0.2.1, rack6-2-con2 192.0.2.2, rack6-3-con3 192.0.2.3)에서 실행합니다. 모두 조회만 합니다.

① o-hm0 IP와 서비스 상태

hostname; ip -br addr show o-hm0; ip route | grep 172.16; systemctl is-active octavia-interface

172.16.0.x/22 주소가 없거나 서비스가 inactive이면 조치 대상입니다.

② OVS 연결 상태

ovs-vsctl get Port o-hm0 tag; ovs-vsctl get Interface o-hm0 external_ids ofport

tag가 숫자(4095 아님)이고 ofport가 양수이면 OVS 연결은 정상입니다.

③ amphora 접속 테스트

openstack loadbalancer amphora list -c id -c status -c lb_network_ip
timeout 3 bash -c "</dev/tcp/<amphora IP>/9443" && echo OPEN || echo CLOSED

2.2 조치: o-hm0 IP 복구

IP가 없는 컨트롤러에서 실행합니다. restart가 아니라 start를 사용하세요. 스크립트의 stop은 OVS에서 o-hm0 포트를 삭제합니다.

systemctl start octavia-interface && sleep 3 && ip -br addr show o-hm0 && ip route | grep 172.16

정상 결과 예시 (rack6-1-con1):

o-hm0            UNKNOWN        198.18.0.2/22
198.18.0.0/22 dev o-hm0 proto kernel scope link src 198.18.0.2

스크립트는 노드별 Neutron 포트(octavia-health-manager-listen-port-<호스트명>)에서 IP를 읽으므로, 반드시 각 노드에서 따로 실행해야 합니다. 노드별 주소는 rack6-1-con1 198.18.0.2, rack6-2-con2 198.18.0.3, rack6-3-con3 198.18.0.4입니다.

2.3 조치 결과 확인

  1. 각 컨트롤러에서 amphora 9443 접속이 OPEN인지 확인
  2. 포털에서 새 로드밸런서를 생성해 2~5분 안에 ACTIVE / ONLINE이 되는지 확인 (이번 조치 후 test-lb-verify가 약 2분 만에 ACTIVE)

2.4 PENDING_CREATE로 멈춘 로드밸런서 정리

o-hm0을 복구해도 이미 실패한 작업은 다시 진행되지 않습니다. PENDING_* 상태는 삭제가 거부되므로 DB에서 상태를 ERROR로 바꾼 뒤 삭제합니다.

① 대상 확인

mysql -e "SELECT id,name,provisioning_status FROM octavia.load_balancer WHERE provisioning_status LIKE 'PENDING%';"

② 상태를 ERROR로 변경

mysql -e "UPDATE octavia.load_balancer SET provisioning_status='ERROR'
  WHERE provisioning_status='PENDING_CREATE' AND id IN ('<LB ID 1>','<LB ID 2>');
  SELECT ROW_COUNT();"

ROW_COUNT가 대상 개수와 같으면 정상입니다. 조건에 PENDING_CREATE를 넣어 다른 로드밸런서는 바뀌지 않습니다.

③ 삭제

포털 [VPC > 로드밸런서]에서 ERROR 상태가 된 항목을 선택하고 삭제합니다. CLI로는 아래와 같습니다. amphora VM, VIP 포트, VIP 보안 그룹도 함께 정리됩니다.

openstack loadbalancer delete --cascade <LB ID>
참고DB를 직접 수정하는 작업이므로 반드시 대상 ID를 확인한 뒤 실행하세요.

2.5 재발 방지 (라이프사이클팀 검토 사항)

  • 주기 점검: octavia-interface는 부팅 시 한 번만 실행되는 oneshot 서비스라 IP가 빠져도 스스로 복구되지 않습니다. o-hm0 IP를 주기적으로 확인해 없으면 재실행하는 systemd timer 또는 모니터링 경보를 추가합니다.
  • IP 고정: netplan 또는 systemd-networkd로 o-hm0 IP를 관리해 네트워크 서비스가 유지하도록 하는 방안을 검토합니다.
  • 리소스: 컨트롤러 3대 모두 Swap 사용률이 96~100%입니다.
  • 로그: rack6-1-con1의 octavia-worker 로그가 수일간 비어 있습니다. worker가 작업을 정상 수신하는지 확인이 필요합니다.
  • 정리 대상: service 프로젝트에 삭제된 로드밸런서의 보안 그룹(lb-378b545c-…)이 남아 있습니다.

3. 로드밸런서 생성 방법

3.1 사전 확인

  • 접속: CONTRABASS 포털(https://console.example.com)에 관리자 계정으로 로그인합니다. 접속 PC의 hosts 파일 설정이 필요합니다(라이프사이클팀 접속 안내 메일 참고).
  • 쿼터: amphora VM은 service 프로젝트에 생성됩니다. 로드밸런서 1개당 VM 2대, vCPU 4개가 필요합니다(service 프로젝트 한도: 인스턴스 10, vCPU 20, 보안 그룹 10).
  • 세그먼트: 로드밸런서를 둘 세그먼트와 서브넷을 정합니다. 외부 접속이 필요하면 외부 라우팅이 Yes인 세그먼트를 선택합니다.

3.2 생성 절차

메뉴: [VPC] > [로드밸런서] > 오른쪽 위 [+ 생성]. 생성 화면은 5단계로 구성되며, 각 단계에서 [다음]을 누릅니다.

단계항목입력 예시 / 설명
① 기본 정보이름 (필수)test-lb-verify
설명선택 입력 (최대 40자)
할당 프로젝트 (필수)handson
세그먼트 (필수)198.51.100.0/24 선택
서브넷 (필수)198.51.100.0/24, 고정 IP는 자동 할당
② 리스너리스너 사용 여부사용 (모니터링에는 Prometheus 리스너가 필요)
이름test-lb-verify-listener
프로토콜 / 포트HTTP / 80
기타 시간 제한값기본값 유지 (연결 제한 -1, 클라이언트 데이터 50000 등)

③ 풀풀 사용 여부트래픽을 분산하려면 사용, 테스트만 할 때는 미사용
④ 풀 멤버풀 멤버 사용 여부트래픽을 받을 VM과 포트 지정. 나중에 추가 가능

마지막 단계에서 [생성]을 누르면 “로드밸런서 생성 요청 성공” 알림이 표시되고 목록으로 돌아갑니다.

3.3 생성 후 확인

시점정상 상태
생성 직후프로비저닝 PENDING_CREATE / 오퍼레이팅 OFFLINE
약 2~5분 후프로비저닝 ACTIVE / 오퍼레이팅 ONLINE
5분 이상 PENDING_CREATE 지속1~2장의 원인과 해결 방법에 따라 컨트롤러 o-hm0 상태를 점검

CLI로 확인할 때는 다음 명령을 사용합니다.

openstack loadbalancer list -c name -c provisioning_status -c operating_status
openstack loadbalancer amphora list -c id -c status -c role -c lb_network_ip

3.4 참고 사항

  • 외부 접속: 외부에서 접속하려면 생성 후 목록의 [⋯] > [유동 IP 연동]으로 유동 IP를 연결합니다.
  • 수정과 삭제: [⋯] 메뉴에서 수정하거나 삭제합니다. PENDING_* 상태에서는 삭제가 되지 않습니다(2.4 참고).
  • 보안 그룹: 로드밸런서마다 VIP 보안 그룹(lb-<ID>)이 자동 생성되고, 삭제 시 함께 정리됩니다.

4. FAQ (자주 묻는 질문)

Q1. 로드밸런서가 PENDING_CREATE에서 멈췄습니다. 기다리면 해결되나요?
정상이라면 2~5분 안에 ACTIVE가 됩니다. 5분이 넘으면 기다려도 바뀌지 않는 경우가 많습니다. 컨트롤러 3대의 o-hm0 IP부터 확인하세요(2.1 참고).
Q2. 포털에서 삭제를 눌러도 아무 반응이 없습니다.
PENDING_CREATE 같은 PENDING_* 상태에서는 Octavia가 삭제 요청을 거부합니다. DB에서 상태를 ERROR로 바꾼 뒤 삭제해야 합니다(2.4 참고).
Q3. octavia-interface를 restart하면 안 되나요?
스크립트의 stop 동작은 OVS에서 o-hm0 포트를 삭제합니다. start만으로 IP가 다시 설정되므로 restart 대신 start를 사용하세요.
Q4. 컨트롤러 한 대만 고치면 되나요?
아니요. 생성 요청은 컨트롤러 3대의 worker 중 하나에 배정됩니다. o-hm0이 고장 난 노드가 하나라도 있으면 그 노드에 배정된 요청은 실패하므로, 3대 모두 확인해야 합니다.
Q5. amphora VM이 ACTIVE인데 왜 로드밸런서는 안 만들어지나요?
VM이 켜진 것과 Octavia가 VM 안의 amphora-agent에 접속할 수 있는 것은 별개입니다. 컨트롤러에서 amphora IP의 9443/tcp로 접속이 되어야 다음 단계로 넘어갑니다.
Q6. 오퍼레이팅 상태가 ONLINE인데 프로비저닝은 PENDING_CREATE입니다.
ONLINE은 amphora의 heartbeat가 health manager에 도착하고 있다는 뜻일 뿐입니다. 생성 작업을 맡은 worker가 이미 실패했다면 프로비저닝 상태는 바뀌지 않습니다.
Q7. anti-affinity 때문에 생성이 실패할 수 있나요?
컴퓨트 호스트가 부족하면 amphora 2대를 서로 다른 호스트에 둘 수 없어 실패할 수 있습니다. 이때는 VM이 ERROR(No valid host)가 되고 로드밸런서도 ERROR로 바뀝니다. 이번 장애는 해당하지 않았습니다.
Q8. 보안 그룹 쿼터 초과도 원인이 될 수 있나요?
네. 2026-03에 같은 환경에서 프로젝트 보안 그룹 쿼터 초과로 생성이 실패한 사례가 있습니다. 이때는 상태가 ERROR로 표시됩니다. 불필요한 로드밸런서를 지우거나 쿼터를 늘려 해결합니다.
Q9. 로드밸런서를 몇 개까지 만들 수 있나요?
1개당 amphora VM 2대(vCPU 4개)가 service 프로젝트에 생성됩니다. 현재 한도(인스턴스 10, vCPU 20)에서는 동시에 최대 5개까지 가능합니다.
Q10. Octavia worker 로그 파일이 비어 있습니다.
해당 노드의 worker가 작업을 맡지 않았을 수 있습니다. 다른 컨트롤러의 /var/log/octavia/octavia-worker.log에서 로드밸런서 ID로 검색해 어느 노드가 처리했는지 확인하세요.

5. 용어 정리

용어설명
OctaviaOpenStack의 로드밸런서 서비스. CONTRABASS 포털의 [VPC > 로드밸런서]가 내부적으로 사용
amphora로드밸런서 역할을 하는 전용 VM. HAProxy가 들어 있으며 service 프로젝트에 생성됨
amphora-agentamphora 안에서 실행되는 관리 프로그램. 9443/tcp로 컨트롤러의 설정 명령을 받음
Octavia worker로드밸런서 생성·수정·삭제 작업을 실제로 수행하는 컨트롤러 프로세스
Health Manageramphora가 보내는 상태 신호(heartbeat)를 받아 오퍼레이팅 상태를 판단하는 프로세스
Housekeeping오래된 리소스 정리, 인증서 갱신 등을 맡는 Octavia 백그라운드 프로세스
heartbeatamphora가 5555/udp로 Health Manager에 주기적으로 보내는 “살아 있음” 신호
lb-mgmt-net컨트롤러와 amphora가 관리 통신을 하는 전용 네트워크 (198.18.0.0/22)
o-hm0컨트롤러를 lb-mgmt-net에 연결하는 가상 인터페이스 (Octavia Health Manager 인터페이스 0번)
octavia-interface부팅 시 o-hm0을 만들고 고정 IP를 넣는 systemd 서비스 (oneshot)
OVS (Open vSwitch)서버 안에서 동작하는 가상 스위치. br-int는 VM 포트들이 연결되는 통합 브리지
NeutronOpenStack의 네트워크 서비스. 포트, 서브넷, 보안 그룹 등을 관리
VIPVirtual IP. 클라이언트가 접속하는 로드밸런서의 대표 IP (예: 198.51.100.134)
리스너로드밸런서가 트래픽을 받는 프로토콜과 포트 설정 (예: HTTP 80)
풀 / 풀 멤버트래픽을 나눠 받을 서버 그룹(풀)과 그 안의 개별 서버(멤버)
헬스 체크풀 멤버가 정상인지 주기적으로 검사하는 기능
프로비저닝 상태생성·변경 작업의 진행 상태 (PENDING_CREATE, ACTIVE, ERROR 등)
오퍼레이팅 상태실제 동작 상태 (ONLINE, OFFLINE 등). heartbeat 수신 여부로 판단
PENDING_CREATE생성 작업이 진행 중인 상태. 이 상태에서는 수정·삭제가 거부됨
ACTIVE_STANDBYamphora 2대를 MASTER/BACKUP으로 두는 이중화 구성
anti-affinity같은 그룹의 VM을 서로 다른 물리 호스트에 배치하도록 하는 규칙
oneshot 서비스한 번 실행하고 끝나는 systemd 서비스 유형. 실행 후 문제가 생겨도 스스로 복구하지 않음
쿼터프로젝트가 만들 수 있는 리소스(인스턴스, vCPU, 보안 그룹 등)의 최대 개수
