CONTRABASS 컴퓨트 서비스

nova-compute DOWN 원인 및 SSH 조치 매뉴얼

항목내용
대상 환경교육센터 CONTRABASS (edu306), OpenStack Nova / RabbitMQ
대상 호스트rack6-1-con1 (192.0.2.1), rack6-2-con2 (192.0.2.2), rack6-3-con3 (192.0.2.3), rack6-4-com1 (192.0.2.4)
작성일2026-11-03
작성자최우성 (교육팀)
요약nova-compute가 컨트롤러의 RabbitMQ로 상태 보고를 하지 못하면 포털에 DOWN으로 표시된다. 이번에는 rack6-3-con3의 메모리 부족(Swap 100%)으로 RabbitMQ 연결이 끊긴 것이 주원인으로 보인다. 이 환경은 파드가 아니라 systemd 서비스라서 systemctl restart nova-compute로 복구한다.

요약

한 줄 요약nova-compute가 DOWN이어도 VM은 계속 동작한다. 해당 호스트에 SSH로 접속해 로그에서 원인(AMQP 연결 끊김, 메모리 부족 등)을 확인하고 systemctl restart nova-compute로 재시작한다. 여러 호스트가 번갈아 DOWN되면 RabbitMQ가 있는 컨트롤러의 자원 상태를 먼저 본다.
구분내용
증상CONTRABASS 대시보드 > 시스템 정보 > 컴퓨트 서비스가 9/10. 특정 호스트의 nova-compute 작동 상태가 DOWN
영향실행 중인 VM은 영향 없음. 해당 호스트에 새 VM 생성·이동·삭제가 실패하고, 스케줄러 배치 대상에서 빠짐 (No valid host 원인이 됨)
주원인nova-compute ↔ RabbitMQ(컨트롤러 5672/tcp) 연결 끊김. 로그에 "AMQP server on 192.0.2.3:5672 is unreachable" 기록
배경 원인rack6-3-con3 메모리 부족(Swap 100%, load 20). 09:07에는 부하 테스트 명령이 실수로 con1에서 실행되어 load 65까지 상승
조치해당 호스트에서 로그 확인 → systemctl restart nova-compute → 포털에서 UP 확인
배포 방식OpenStack이 systemd 서비스로 설치됨. kubectl, docker, crictl이 없으므로 "파드 재기동"이 아니라 "서비스 재시작"으로 조치
남은 과제con3 메모리와 RabbitMQ 안정화, 작성 시점에 DOWN인 rack6-2-con2 nova-compute 복구 (라이프사이클팀 협의)

빠른 점검법: DOWN인 호스트에 접속해 아래 두 명령으로 서비스 상태와 최근 오류를 먼저 확인하세요.

systemctl is-active nova-compute
grep -E "AMQP|unreachable|ERROR" /var/log/nova/nova-compute.log | tail -10

1. 환경 구성 이해

1.1 호스트 구성

호스트IP역할
rack6-1-con1192.0.2.1컨트롤러 + 컴퓨트 (nova-scheduler, nova-conductor, nova-compute, RabbitMQ 등). admin_openrc 있음
rack6-2-con2192.0.2.2컨트롤러 + 컴퓨트
rack6-3-con3192.0.2.3컨트롤러 + 컴퓨트. admin_openrc 없음 (openstack 명령은 con1에서 실행)
rack6-4-com1192.0.2.4컴퓨트 전용 (nova-compute). VIOLA 클러스터 노드와 amphora가 실행 중
주의컨트롤러 3대도 VM을 실행하는 컴퓨트 역할을 함께 한다. 컨트롤러에 부하를 주면 OpenStack 제어 기능과 그 위의 VM이 동시에 영향을 받는다.

1.2 배포 방식: 파드가 아니라 systemd 서비스

con3에서 실제로 확인한 결과, 쿠버네티스나 컨테이너 도구가 설치되어 있지 않았다. OpenStack 구성 요소는 Ubuntu 패키지로 설치되어 systemd 서비스로 동작한다.

root@rack6-3-con3:~# kubectl get nodes        → Command 'kubectl' not found
root@rack6-3-con3:~# docker ps -a             → Command 'docker' not found
root@rack6-3-con3:~# crictl ps -a             → Command 'crictl' not found
root@rack6-3-con3:~# systemctl list-units --all | grep -iE "nova|libvirt"
  nova-compute.service   loaded active running  OpenStack Compute
  nova-conductor.service loaded active running  OpenStack Compute Conductor
  libvirtd.service       loaded active running  libvirt legacy monolithic daemon
배포 방식확인 방법재기동 방법
systemd 서비스 (이 환경)systemctl status nova-computesystemctl restart nova-compute
쿠버네티스 파드 (openstack-helm 등)kubectl get pods -A -o widekubectl -n <ns> delete pod <파드> (자동 재생성)
컨테이너 (kolla 등)docker ps -a | grep novadocker restart nova_compute

1.3 nova-compute 상태(UP/DOWN)가 정해지는 방식

  1. 각 호스트의 nova-compute는 주기적으로(기본 10초) 자신의 상태를 보고한다.
  2. 보고는 컨트롤러의 RabbitMQ(메시지 큐, 5672/tcp)를 거쳐 nova-conductor가 DB에 기록한다.
  3. 마지막 보고가 일정 시간(기본 60초) 넘게 없으면 해당 서비스를 DOWN으로 판단한다.
  4. CONTRABASS 대시보드의 컴퓨트 서비스 상태는 이 값을 그대로 보여 준다.
핵심DOWN은 "VM이 꺼졌다"가 아니라 "상태 보고가 끊겼다"는 뜻이다. 프로세스가 살아 있어도(active) RabbitMQ 연결이 끊기면 DOWN이 될 수 있다.

2. nova-compute가 DOWN 되는 이유

2.1 오늘의 경과

시각내용
11-02 14:05rack6-3-con3 nova-compute / 하이퍼바이저 UP→DOWN (알람 센터 기록). 대시보드 컴퓨트 9/10
11-03 09:07부하 테스트 명령이 webserver01이 아닌 rack6-1-con1에서 실행됨 → yes 프로세스 약 96개, CPU 유휴 0%, load 65. pkill yes로 즉시 정리
09:26con3 접속. Swap 100%, load 20.32 확인
09:33con3에서 systemctl restart nova-compute → con3 UP
09:35:18com1 로그: "AMQP server on 192.0.2.3:5672 is unreachable … Connection reset by peer" → com1 DOWN
09:38com1에서 systemctl restart nova-compute → com1 UP (09:39:44 기준)
09:39:44rack6-2-con2 nova-compute DOWN (작성 시점 기준 조치 필요)

2.2 원인 ① RabbitMQ 연결 끊김 (주원인)

com1의 nova-compute 로그에서 con3의 RabbitMQ가 연결을 끊은 기록이 확인됐다. 3초 뒤 다시 연결됐지만, 그 사이 상태 보고가 빠져 DOWN으로 표시됐다.

2026-11-03 09:35:18.047 ERROR oslo.messaging._drivers.impl_rabbit [-] AMQP server on
  192.0.2.3:5672 is unreachable: <RecoverableConnectionError: unknown error>.
2026-11-03 09:35:18.048 INFO ... trying to reconnect: [Errno 104] Connection reset by peer
2026-11-03 09:35:21.057 INFO ... Reconnected to AMQP server on 192.0.2.3:5672

한 호스트를 복구하면 다른 호스트가 DOWN되는 식으로 번갈아 나타나면, 개별 nova-compute보다 공통으로 쓰는 RabbitMQ 쪽 문제일 가능성이 크다.

2.3 원인 ② 호스트 자원 부족 (배경 원인)

호스트관측 값의미
rack6-3-con3Swap 100%, load 20.32, Memory 67%스왑이 가득 차 프로세스 응답이 느려짐. RabbitMQ가 연결을 끊는 원인이 될 수 있음
rack6-4-com1Swap 54% (4.4/8.0 GiB), load 14.5여유는 있으나 스왑 사용 중
rack6-1-con109:07 load 65, CPU 유휴 0%부하 테스트 실수로 일시 과부하. 정리 후 유휴 80%로 회복

2.4 그 밖의 원인 후보

  • nova-compute 프로세스가 멈춤(hang): systemctl은 active지만 로그가 더 이상 쌓이지 않음
  • libvirtd 응답 없음: nova-compute가 하이퍼바이저 정보를 못 가져와 보고가 지연됨
  • 시간 동기화 오류: 호스트 시간이 어긋나면 보고 시각이 오래된 것으로 판단될 수 있음 (timedatectl로 확인)
  • 네트워크 문제: 호스트 ↔ 컨트롤러 5672/tcp 통신 불가

2.5 DOWN 상태의 영향

구분영향
실행 중인 VM영향 없음. 포털에서도 ACTIVE / RUNNING으로 표시되고 서비스는 계속됨
새 VM 생성해당 호스트는 스케줄러 대상에서 빠짐. 남은 호스트에 자원이 없으면 "No valid host was found"로 실패
VM 조작해당 호스트 VM의 시작/중지/삭제/이동 요청이 처리되지 않거나 지연됨
로드밸런서amphora VM 생성이 실패하거나 지연되어 PENDING_CREATE, ERROR가 늘어날 수 있음
오토스케일복제 VM 생성 실패 (4장 참고)

3. SSH 접속을 통한 해결 방법

3.1 접속

계정 정보는 라이프사이클팀 접속 안내 메일을 참고한다. 비밀번호는 직접 입력한다.

ssh root@192.0.2.3      # DOWN인 호스트의 IP로 접속
필수명령을 실행하기 전에 프롬프트가 의도한 호스트인지 반드시 확인한다 (예: root@rack6-3-con3). 오늘 부하 테스트 명령이 컨트롤러에서 실행된 실수가 있었다.

3.2 서비스 상태 확인

systemctl status nova-compute --no-pager | head -15
systemctl list-units --all | grep -iE "nova|libvirt"
  • Active: failed / inactive → 재시작 대상
  • Active: active (running)인데 포털은 DOWN → RabbitMQ 연결이나 프로세스 멈춤을 의심하고 로그 확인

3.3 로그 확인

이 환경은 journalctl에 nova-compute 기록이 남지 않는다("-- No entries --"). 로그 파일을 직접 본다.

tail -30 /var/log/nova/nova-compute.log
grep -E "AMQP|unreachable|ERROR" /var/log/nova/nova-compute.log | tail -10
로그 문구의미와 대응
AMQP server … is unreachable / Connection reset by peerRabbitMQ 연결 끊김 → 재시작 후 RabbitMQ가 있는 컨트롤러 자원 점검
MessagingTimeout컨트롤러 응답 지연 → nova-conductor, RabbitMQ 상태 확인
Out of memory / Cannot allocate memory메모리 부족 → free -h, 메모리 상위 프로세스 확인
libvirt 관련 오류하이퍼바이저 문제 → 라이프사이클팀 문의 (libvirtd 임의 재시작 금지)

3.4 자원 확인

free -h; uptime
ps aux --sort=-%mem | head -10

3.5 nova-compute 재시작

systemctl restart nova-compute
systemctl is-active nova-compute      # active 이면 정상

nova-compute만 재시작하는 것은 이 호스트에서 실행 중인 VM에 영향을 주지 않는다.

3.6 복구 확인

  1. 1~2분 뒤 CONTRABASS 대시보드 > 시스템 정보 > 컴퓨트 서비스를 클릭해 해당 호스트가 UP인지 확인한다.
  2. CLI로 확인하려면 con1에서 실행한다 (con3에는 admin_openrc가 없음). 
    ssh root@192.0.2.1
source admin_openrc
openstack compute service list --service nova-compute
  3. 복구 직후 다른 호스트가 DOWN되는지 몇 분간 지켜본다. 번갈아 DOWN되면 3.7로 넘어간다.

3.7 근본 원인 조치 (RabbitMQ·메모리)

systemctl status rabbitmq-server --no-pager | head -10
free -h
ps aux --sort=-%mem | head -10
협의 필요RabbitMQ는 OpenStack 전체가 쓰는 메시지 큐라서 재시작하면 모든 서비스에 잠시 영향이 간다. RabbitMQ 재시작이나 메모리 정리는 라이프사이클팀과 협의한 뒤 진행한다.

3.8 하지 말아야 할 것

금지 항목이유
libvirtd 재시작해당 호스트의 VM(VIOLA 클러스터 노드, amphora, 교육생 VM) 실행에 영향
openvswitch / neutron 에이전트 재시작VM과 로드밸런서 네트워크가 끊길 수 있음
협의 없는 RabbitMQ 재시작OpenStack 전체 API와 서비스가 잠시 멈춤
프롬프트 확인 없이 명령 실행컨트롤러에 부하 명령이 실행되는 사고 발생 (11-03 09:07 사례)
컨트롤러에서 부하 테스트제어 기능 전체가 느려지고 다른 교육생 환경에 영향

4. 참고: 오토스케일 실패와 "No valid host"

같은 날 로드밸런서 오토스케일(임계치 설정) 테스트에서 복제 VM(webserver01-asg-01)이 ERROR가 됐다. 포털 작업 이력에는 "No valid host was found"만 보였지만, com1의 nova-compute 로그에 실제 원인이 있었다.

nova.exception.InvalidInput: Invalid input received: Image e1253e34-… is unacceptable:
  Image virtual size is 20GB and doesn't fit in a volume of size 10GB. (HTTP 400)
Build of instance a0401b0f-… aborted
구분내용
원인복제 VM의 루트 볼륨 10GB < 원본 이미지 가상 크기 20GB → 볼륨 생성 실패 → 빌드 중단
포털 표시"No valid host was found" (재시도할 호스트가 없어 함께 표시됨)
해결로드밸런서 생성 > 풀 멤버 > 임계치 설정 > 기준 인스턴스 정책에서 볼륨을 20GB 이상으로 지정 (풀 수정 화면에서는 임계치 변경 불가)
교훈"No valid host"는 자원 부족만 뜻하지 않는다. 대상 호스트의 nova-compute.log에서 실제 오류를 확인한다

5. FAQ (자주 묻는 질문)

nova-compute가 DOWN이면 그 호스트의 VM도 꺼진 건가요?
아닙니다. 상태 보고가 끊긴 것일 뿐 VM은 계속 동작합니다. 다만 새 VM 생성이나 VM 조작은 실패할 수 있습니다.
"파드 재기동"으로 해결하라는데 kubectl이 없어요.
이 환경은 쿠버네티스가 아니라 systemd 서비스로 설치되어 있습니다. systemctl restart nova-compute가 같은 역할을 합니다.
systemctl status는 active인데 포털은 DOWN이에요.
프로세스는 살아 있지만 RabbitMQ 연결이 끊겼거나 멈춘 상태일 수 있습니다. 로그에서 AMQP 오류를 확인하고 재시작하세요.
journalctl에 아무것도 안 나와요.
이 환경은 /var/log/nova/nova-compute.log 파일에 로그를 씁니다. tail이나 grep으로 파일을 직접 보세요.
한 호스트를 고치면 다른 호스트가 DOWN돼요.
공통으로 쓰는 RabbitMQ나 컨트롤러 자원 문제일 가능성이 큽니다. RabbitMQ가 있는 컨트롤러의 메모리와 Swap을 확인하고 라이프사이클팀과 협의하세요.
nova-compute를 재시작하면 VM이 재부팅되나요?
아닙니다. nova-compute 재시작은 실행 중인 VM에 영향을 주지 않습니다. libvirtd 재시작은 영향이 있으니 하지 마세요.
con3에서 openstack 명령이 "Missing value auth-url" 오류가 나요.
admin_openrc를 적용하지 않아서입니다. con3에는 admin_openrc 파일이 없으니 con1에서 source admin_openrc 후 실행하세요.
부하 테스트를 컨트롤러에서 실수로 실행했어요.
즉시 pkill yes(또는 pkill stress-ng)로 중지하고, pgrep -c yes가 0인지, top의 유휴(id)가 회복됐는지 확인하세요.

용어설명
nova-compute각 호스트에서 VM 생성·삭제를 실제로 수행하고 상태를 보고하는 Nova 서비스
nova-scheduler새 VM을 어느 호스트에 올릴지 고르는 서비스
nova-conductornova-compute 대신 DB에 접근하고 작업을 중계하는 서비스
RabbitMQOpenStack 서비스들이 메시지를 주고받는 메시지 큐. 5672/tcp 사용
AMQPRabbitMQ가 사용하는 메시지 전송 프로토콜
하이퍼바이저VM을 실행하는 소프트웨어. 이 환경은 KVM/libvirt
libvirtdKVM VM을 관리하는 데몬. 재시작하면 VM에 영향
systemd / systemctlLinux 서비스 관리자와 그 명령어. 서비스 시작·중지·재시작·상태 확인
파드(Pod)쿠버네티스에서 컨테이너를 실행하는 최소 단위. 이 환경의 OpenStack에는 해당 없음
Swap메모리가 부족할 때 디스크를 메모리처럼 쓰는 영역. 100%면 시스템이 크게 느려짐
load average실행 대기 중인 작업 수의 평균. CPU 코어 수보다 크게 높으면 과부하
