## 1. 요약

1. **구현 오류 (A유형, 즉시 판단 필요) — 개인 레벨 상한 5.0이 없다.** 레벨 5 구성원이 차원을 1개만 충족해도 5.2, 5개 충족 시 6.0이 월 점수로 계산된다. d22cd9f가 직군별 캡을 지우면서 정의서의 "상한 5.0"을 대신 넣지 않았다.
2. **구현 오류 (A유형) — 최종 점수 반올림 미구현.** 정의서 v6은 "소수점 둘째 자리 반올림 → 첫째 자리 표기값으로 등급 비교"인데, 코드는 2자리까지만 반올림하고 **원값으로 등급을 비교**한다. 3.75 → B(기대) vs C(실제), 3.45 → C vs D, 4.25 → S vs A. 등급이 한 단계 낮게 나오는 경계값이 생긴다.
3. **일치 — 선행 차원 조건 삭제.** 차원 독립 +0.2는 5f3fa41(2026-09-04, **v6 초안 작성 2026-10-06보다 먼저**)로 이미 반영·배포되어 있다. 따라서 "3Q 소급"의 실질 영향은 9/4 이전에 저장된 값에 한정된다(§7).
4. **미완 — M/M→M/D 표기.** 일지 화면은 M/D, KPI 화면·상수·엑셀 컬럼은 M/M이 남아 있다. 계산 단위(8h = 1)는 일관된다.
5. **문서 쪽 정리 필요(B유형).** 가용 M/D는 "해당 월 평일 × 1.0, 휴일·연차 포함(분모에서 빼지 않음)"으로 이미 운영 중이다. 정의서 문구를 이 정의에 맞추는 것을 권장한다.
6. **일정 위험 높음.** 3Q 확정 통보 마감은 **2026-10-08(목)**(공휴일 10/3·10/5 제외, 영업일 5일). 기준일 10/7 기준 **잔여 1영업일**. 코드 수정·배포가 마감 안에 들어가기 어렵고, 정의서는 아직 팀장·본부장 승인 전이다.
7. 사이트 표시본 `교육팀 KPI 정의서`는 **v5 그대로**이며 v6 반영분이 없다(§2-1).

**TMS의 가용 M/D 산출 방식 (코드 기준)**

- 분모(가용): 해당 월의 평일 키(`getMonthWeekdayKeys`, 월 밖 날짜 제외 — #148) × **1.0/일**. 공휴일·연차·반차를 **빼지 않는다**.
- 분자: 업무 + 생산성향상 + **휴일 M/D**(연차 1.0, 반차 0.5, 반반차 0.25, 공휴일 1.0). 일지 미등록일은 `resolveJournalDay` 규칙(2026 공휴일이면 휴일 1.0).
- 토요일 공휴일(8/15, 9/26)은 평일 키가 아니므로 분모·분자 모두에서 제외(#148).
- 신규 입사·장기 휴직: 별도 처리 없음. 모든 구성원이 같은 평일 수를 분모로 사용.
- 팀 가동률: 구성원별 월 값을 합산해 비율 계산(`buildTeamIntegratedSummary`).
- 월 확정값(`monthly01`)이 입력되면 일지 계산값보다 우선(`computeTeamKpi.js:289-297`). #149는 「일지에서 가져오기」·제출 시 일지 기준값 `journalAvailable`을 쓰도록 수정. #157은 저장값과 일지 집계가 0.05 초과로 다르거나 가동률이 100.05%를 넘으면 배지만 표시(데이터 불변).
- 초과(100% 초과): 계산에서 상한 처리 없음. `sumDayMm`만 일 단위 `Math.min(1, …)`이며 월 합계 경로의 적용 여부는 **미확인**.

1. **가용 M/D 문구(필수, B유형):**

3. **반올림 문구:** "half-up(0.05 이상 올림)" 명시, 가동률·생산성 등급은 반올림 없이 원값 비교(현재 동작)라는 점을 적을지 결정(미확정 항목).

6. **리더 평가·자체평가 통합(미확정):** 시스템은 자체평가를 레벨 축과 리더 축에 각각 입력해 사용 중이므로, v6 문구("1종 통합")를 확정하려면 데이터 모델 차이를 먼저 맞춰야 한다. 확정 전까지 문서만 선반영하지 않기를 권장.
7. **2Q 목표 3.2 vs C등급 3.5 불일치:** 현행 유지(보류) — 해석 문구만 한 줄 추가할지 결정.

- **과거 수치 영향 산출:** 월 `computed.proposed`·분기 `level`·`composite`·`grade`가 저장되는 구조라 **영향 건수·변동폭은 저장 데이터를 열람해야 산출 가능 → 미확인**. 운영 데이터 열람 없이 쓸 수 있는 방법: (a) 읽기 전용 스크립트로 `competencyMonths`의 `dims`·`intLevel`에서 구 규칙(연속 체인+캡)과 신 규칙 결과를 비교 출력(쓰기 없음), (b) 분기 레코드의 `composite`를 새 반올림 규칙으로 재판정만 해서 등급 변경 건수 확인. 둘 다 **제안만** 하며 실행하지 않았다.
- **영향을 받을 수 있는 방향:** 새 규칙(독립 +0.2, 캡 없음)은 가산을 늘리기만 하므로 레벨은 같거나 **올라간다**. 반올림 규칙(②)은 경계에서 등급이 **올라간다**(3.75 C→B 등). 5.0 상한(①)만 점수를 낮추며 대상은 레벨 5 구성원뿐이다. 즉 **등급이 내려가는 구성원은 상한 5.0 적용 대상(레벨 5 보유자) 외에는 없을 것으로 보이나**, 레벨 5 보유 여부는 **미확인**.
- **산식 버전 분기(설계안만):** 분기 레코드에 `ruleVersion`(`v5`/`v6`)을 두고 `computeCompetencyEval`·`gradeKpi3`에 버전 인자를 전달, 기본값은 `v5`(과거 보존), 3Q 이후만 `v6`. 단 3Q에 소급이면 **분기 기준 전환**이 아니라 **3Q 이후 일괄 v6**이어야 하며 2Q 이전 레코드는 `v5` 유지. 저장 스키마 변경(`ruleVersion` 필드 추가)은 Supabase/로컬 스토리지 마이그레이션이 필요하므로 **SQL/계획만 제안**. 현재는 버전 필드가 없어 분기 판별만으로도 구현할 수 있다(`quarterKey` ≥ `2026-3Q` → v6)는 대안이 있다.
- 영향 코드·문구·테스트: §5 표 참조. 화면 문구 변경이 많은 쪽은 ③(M/D).

## 8. 결정이 필요한 항목

1. **상한 5.0:** 어디에 적용할지 — (가) 월 점수 계산 시점 `proposedComposite`(권장, 조회·저장 값 모두 5.0 이하), (나) 분기 롤업·평균 단계. 직군별 예외 없음 확인 필요.
2. **반올림:** 첫째 자리 half-up을 `gradeKpi3`에서 적용하고, 이미 저장된 `quarter.composite`/`grade`는 (가) 건드리지 않고 조회 시 재판정 / (나) 저장 값 유지(과거 확정 분기 보존) 중 선택. 3Q 소급이면 (가).
3. **3Q 확정 일정:** 마감 10/8. 현행 산식으로 먼저 통보할지, 연기할지, 정정 통보 절차를 둘지.
4. **M/D 표기 범위:** 화면 문구만 / 엑셀 컬럼 포함 / 식별자까지.
5. **v6 초안 항목(리더 평가, 자체평가 통합) 확정 여부:** 확정 전 코드 변경 없음.
6. **미확정 항목 답변 필요:** 신규·장기 휴직 평균 제외 방식(입사일 모델 필요), 가용 M/D 초과 처리, 기준표 역할 비중 산정, 실전 적용 5점 척도 재정의, 다면 N 미달 규칙, 승인 기한 구현 범위.
7. **원문 docx 제공 여부:** 변환본 대조를 위해 필요.
