## 2. 항목별 변경안

### A. Level 4 이상 본부장/CEO 승인

**현재:** 승인 상태는 `KPI_STATUS`(작성중/제출/승인/반려) 하나뿐이고(`src/constants/kpiStatuses.js`), 승인 주체는 관리자 화면의 팀장이다(`KpiApprovePage.jsx`, `kpiApprovePendingApprovals.js`). 월 확정 `monthly01`에 `approver`·`approvedAt`(문자열)이 있으나 상위 승인 구분은 없다. 본부장/CEO는 TMS 사용자가 아니다.

**제안 (기록형):** 상위 승인은 TMS 밖에서 이뤄지므로 TMS에는 **승인 사실을 기록**한다.
- 분기 레코드에 `execApproval: { required, approver, approvedAt, evidenceNote }` 추가 (`defaultQuarterRecord`, `kpiOperationalStore.js:75`).
- `required`는 개인 분기 레벨 ≥ 4일 때 자동 `true` (계산 시 판정, 저장은 기록 시점).
- `lockKpi3Quarter`(분기 확정, `useKpiOperational.js:580`)에서 `required && !approvedAt`이면 확정을 막고 사유를 안내하거나, 경고만 표시하고 허용(선택).
- UI: `Kpi3ElementsPanel.jsx`의 분기 확정 버튼 위에 "상위 승인 기록(승인자·일자·증빙 메모)" 입력. `KpiApprovePage`에는 "상위 승인 필요" 배지.

| 선택지 | 내용 | 장단점 |
|---|---|---|
| **A1 기록형 (권장)** | 팀장이 승인자·일자를 기록 | 인증 변경 없음, 가장 작음. 실제 승인 여부는 신뢰 기반 |
| A2 승인 역할 신설 | 본부장/CEO 계정으로 TMS에서 승인 | 접근 모델·인증(`teamAccess`, `adminGate`) 변경 필요, 대규모 |
| A3 문서만 정리 | 상위 승인은 운영 절차로 두고 문서 문구 완화 | 구현 없음. 승인된 v6와 다시 어긋남 |

- **저장:** JSON 필드 추가만으로 가능(`kpi_operational_snapshots` 페이로드). DB 스키마 변경 불필요. 기존 레코드는 필드가 없으면 `required` 계산값만 사용.
- **테스트:** `defaultQuarterRecord` 기본값, 레벨 4 경계(3.9 vs 4.0), 확정 차단/경고 분기, 정규화 시 기존 데이터 호환.
- **위험:** 3Q 이미 확정된 레코드는 소급 적용하지 않음(필드 없으면 통과).

### B. 확정 통보·이의 제기 (분기 말 + 5영업일)

**현재:** 분기 확정(`quarter.locked`, `confirmedAt`)만 있고 영업일 계산, 통보 일자, 이의 접수·검토 기록이 없다. 공휴일 데이터는 `src/data/krPublicHolidays2026.js`(2026년만).

**제안:**
1. 유틸 `addBusinessDays(date, n)` / `quarterNoticeDeadline(yq)` 신설(주말·공휴일 제외). 3Q = 2026-10-08 (10/3·10/5 제외)이 기대값이며 이 케이스를 단위 테스트에 고정.
2. 분기 레코드에 `noticedAt`(확정 통보일)과 `appeals[]`(접수일, 내용, 단계: 접수→팀장 1차→본부장 2차→종결, 처리자·처리일) 추가.
3. UI: 분기 확정 영역에 "통보 마감 D-n", 통보일 기록, 통보 후 5영업일 이내 이의 접수 기한 표시. 이의는 기록·상태 관리만(알림 발송 없음).
4. 2027년 이후 공휴일 데이터가 없으므로 연도 확장 또는 "공휴일 데이터 없음" 경고를 함께 처리.

- **저장:** JSON 필드 추가. 이의를 별도 테이블로 분리하려면 `supabase/schema.sql` 변경(SQL 제안만, 실행하지 않음). 초기에는 JSON 권장.
- **데이터 안전:** 기존 레코드 불변, 필드 누락 시 "미기록".
- **테스트:** 영업일 계산(연휴·주말 경계), 마감 계산(분기 말 포함 여부 — "분기 말로부터 5영업일"을 분기 말 다음 영업일부터 1일로 센다는 해석을 문서와 확인).

### C. 신규 입사·장기 휴직자 평균 제외

**현재:** `TEAM_KPI_MEMBERS`(`kpiMembers.js`)에 입사일·휴직 정보가 없다. 팀 평균은 `averagePositive`(`teamKpiAggregate.js:15`)가 값이 0 이하인 구성원을 암묵적으로 뺀다. 그래서 (1) 제외 사유와 입력 누락이 구분되지 않고 (2) 요소마다 분모가 달라질 수 있으며 (3) 최소 인원 규칙이 없다.

**제안:**
- 구성원 설정에 `joinedAt`, `leaves: [{ from, to }]` 추가.
- `isEligibleForQuarter(member, yq)` 신설(입사 후 1분기 미만, 장기 휴직 기간 → 제외). 평균 대상은 이 함수로 결정하고 `averagePositive`의 값 기준 제외는 폐기.
- 미입력 구성원은 제외하지 않고 "미입력" 경고(분모에는 포함, 종합은 잠정 표시 — 이미 배포된 부분 입력 배지와 연동).
- 화면: 팀 평균 옆에 "대상 n명 / 제외 m명 (사유)".
- 가용 M/D: 제외 대상의 가용 M/D 산정은 문서에 `[확정 필요]`이므로 **이 항목에 포함하지 않는다.**

- **결정 필요:** 장기 휴직 기준 기간, 제외 후 평균 대상이 1~2명일 때 최소 인원(문서에 없음).
- **영향:** 현재 구성원 3명은 모두 대상이라 기존 수치 변화 없음. 값이 0이던 구성원이 평균에서 빠지던 동작이 "미입력 경고"로 바뀌므로 3Q 화면 표시가 달라질 수 있음.
- **테스트:** 입사 1분기 미만/이상 경계, 휴직 기간 겹침, 평균 대상 0·1·2명, 미입력 처리.

### D. 팀장 본인의 리더 평가

**현재:** `computeLeaderScore`(`kpi3ElementScores.js:119`)는 모든 구성원에게 `자체 40% + 평가 60%`를 적용한다. 팀장 본인(`isLeader`)에게도 같은 식이며, 입력 라벨이 "팀장 평가"라 본부장 평가라는 점이 드러나지 않는다.

**제안:** 산식은 그대로 두고 `Kpi3ElementsPanel.jsx`에서 대상이 팀장이면 라벨을 "본부장 평가(60%)"로 바꾸고 안내 문구 추가. 변경 규모 소, 계산·저장 불변.

### E. 실전 적용 "증빙 미제출 = 1점"

**현재:** `computePracticeScore`(`kpi3ElementScores.js:144`)는 사례 0건이면 `null`(점수 없음)이라 평균에서 제외되고, 인정 0건 + 제출 ≥1이면 2점이다. 문서의 1점("증빙 미제출 또는 미인정")은 도달할 수 없다.

**제안:** 분기 확정(`lockKpi3Quarter`) 시점에 점수가 없으면 1점으로 확정(입력 중에는 `null` 유지). "제출 없음" 확정 버튼을 명시하는 방식도 가능.

- **문서와 겹침(미확정):** "2점(제출했으나 일부만 인정)"과 인정 1건(3점)의 경계는 미확정이라 코드를 바꾸지 않는다(현재: 인정 0건·제출 ≥1 → 2점).
- **테스트:** 제출 0건 확정 시 1점, 입력 중 `null`, 인정 건수 경계.

### F. 다면 평가 N 미달 규칙 (미확정 — 차이만 기록)

| 규칙 | 문서 | 코드 (`computeDmScore`) |
|---|---|---|
| 강의 3≤N<5, 전분기 없음 | 규칙 없음 | 당분기만 사용 |
| 운영 N<3, 전분기 없음 | 당분기 팀 레벨로 대체 | `teamLevelFallback`이 있을 때만 대체. 패널은 **팀 평균이 아닌 해당 구성원의 분기 레벨**을 넘김(`Kpi3ElementsPanel.jsx:413`), 값이 없으면 점수 없음 |
| 강의·운영 모두 3건 미만 | 운영 대체 규칙 적용 | 위와 동일 |
| 직군별 프로필 | 문서에 없음 | 강사=강의 100%, 겸업=가중 30~70%(기본 40:60), 기획/운영=운영 중심 (`kpi3DmProfile.js`) |

문서가 확정되기 전에는 코드를 바꾸지 않는다. 확정 시 "팀 레벨" 정의(팀 평균 vs 개인 레벨)와 직군 프로필의 문서 반영 여부가 선행 결정이다.

### G. 기준표별 역할 비중 (보류)

문서에 `[비중 산정 방식 확정 필요]`. 현재는 직무 → 기준표 1개(`mapMemberRoleToCompetency`)이며 겸업은 `concurrent` 기준표를 쓴다. 산정 방식이 정해지기 전에는 구현하지 않는다.

### H. 확정 전 초안 3항목 (보류)

- 리더 평가 등급 환산 "낮은 등급": 코드에 `leaderScoreFromKpiGrades`(둘 중 낮은 등급)가 **참고 제안값**으로 이미 있음. 확정 시 제안값을 기본 입력으로 쓸지 결정.
- 리더 평가 산식 분리(팀원/팀장 본인): 산식 자체는 동일(§2-D).
- 자체평가 1종 통합: 현재 월간 역량 자체평가와 리더 평가용 자체평가가 별도 입력. 통합 시 데이터 모델·UI 변경(대), 승인 후 별도 설계.

## 4. 3Q 확정 일정 대응 (2026-10-08 마감)

코드 변경 없이 운영으로 처리한다.
1. 월간 역량: 7·8·9월 팀장 확정 → 「월간 확정 평균 → 분기 레벨 반영」(구성원별).
2. 다면 평가·리더 평가·실전 적용 입력 및 제출 (현재 김윤형 외 구성원은 미입력 상태).
3. 4요소 입력 완료 확인(화면의 "일부 요소 미입력" 배지가 없어야 함).
4. 레벨 4 이상 구성원이 있으면 증빙 첨부와 본부장/CEO 승인을 문서·메일 등 기존 방식으로 받는다(시스템 기록은 A 구현 전까지 메모로 남김).
5. 분기 확정 후 10/8까지 확정 통보. 이의 제기는 통보 후 5영업일이 기준이다. 10/8에 통보하면 10/9(한글날)을 빼고 10/12~10/16이 5영업일이라 **10/16까지**이며, 별도 기록해 둔다.
6. 마감 내 입력이 어렵다면 확정 통보 연기 또는 정정 통보 절차를 팀장·본부장과 먼저 정한다.

5. F·G·H: 문서 확정 여부.
