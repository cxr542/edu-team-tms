VIOLA 3.0.6 Kiali MSA 네트워크 트래픽 모니터링 구성 가이드

Oct 28, 2026 · @김윤형

개요

VIOLA 3.0.6의 트래픽 모니터링(Kiali) 화면에서 MSA 서비스 간 호출 흐름을 실시간으로 보여 주는 시험 환경을 academy 네임스페이스에 구성하고, 그 절차와 시연 방법을 정리한 문서입니다.

  • 목적: Ingress로 들어온 요청이 msa-a → msa-b → msa-c로 이어지는 흐름, 초당 요청 수, 응답 시간, 성공률을 그래프로 시연합니다.

  • 결과: istio-gateway → msa-a → msa-b(v1, v2) → msa-c 그래프에 Traffic Animation과 요청 수 표시까지 확인했습니다.

  • 환경: VIOLA 3.0.6 biz 클러스터, Istio 1.29.5, Kiali v2.26.1, 시험 네임스페이스 academy, 이미지는 사내 Harbor의 edu-harbor.example.com/library/nginx:latest를 사용했습니다.

  • 전제: 이 시험 구성은 임시용이며, 시연이 끝나면 정리 절차로 원래 상태로 되돌릴 수 있습니다.

구성도

트래픽 흐름과 모니터링 구성 · 5개 구성요소, 측정값 경로

요청은 부하 파드에서 istio-gateway를 거쳐 msa-a → msa-b → msa-c로 흐릅니다. 사이드카가 붙은 파드와 게이트웨이가 측정값을 Prometheus로 보내면, Kiali가 이를 읽어 VIOLA 화면에 그래프로 그립니다. 점선 박스인 부하 파드는 의도적으로 사이드카를 붙이지 않았습니다.

사전 확인 사항

구성 전에 아래 네 가지만 확인하면 되고, 특히 이미지 주소와 사이드카 주입 상태가 중요합니다.

항목 확인 내용 확인 방법
트래픽 모니터링 메뉴 VIOLA 메뉴에 모니터링 → 트래픽 모니터링이 보이고 Kiali 화면이 열림 VIOLA 포털
이미지 노드에 외부 인터넷이 없고 AlwaysPullImages가 켜져 있어, 매번 사내 레지스트리에서 받아야 함. 시험에는 Harbor의 edu-harbor.example.com/library/nginx:latest를 사용 kubectl -n academy run t --image=edu-harbor.example.com/library/nginx:latest --rm -it --restart=Never -- true
리소스 쿼터 academy에 ResourceQuota가 없어 사이드카 추가로 인한 자원 제한이 없음 kubectl -n academy get resourcequota
외부 접속 HAProxy가 80→istio-gateway(32080)로 전달하며, 도메인 DNS가 없으면 VIP 192.0.2.67에 Host 헤더를 직접 지정해 시험 curl -H "Host: 도메인" http://192.0.2.67/

academy의 Istio Injection은 평소에 비활성 상태였습니다. 활성화한 뒤에 새로 만든 파드에만 사이드카가 붙으므로, 다음 절차의 순서를 지켜야 합니다.

구성 절차

순서는 Istio Injection 활성화 → 시험 앱 배포 → 부하 파드 → 멀티 파드 → 확인입니다. 모든 kubectl 명령은 클러스터 마스터 노드(biz-3)에서 실행합니다.

1. Istio Injection 활성화

  1. VIOLA의 네임스페이스 관리에서 academy를 열어 Istio Injection 설정 토글을 활성화로 바꿉니다.

  2. 네임스페이스에 istio-injection=enabled 라벨이 붙습니다. 확인은 아래 명령으로 합니다.

kubectl get ns academy --show-labels

이미 떠 있는 파드는 바뀌지 않고, 새로 만들어지는 파드에만 사이드카(istio-proxy)가 들어갑니다. 반대로 토글을 끄도 이미 사이드카가 붙은 파드는 그대로 유지됩니다.

2. 시험 앱 배포

msa-demo.yaml 하나로 아래 오브젝트를 한 번에 만듭니다. 모든 오브젝트에 demo: kiali-msa 라벨이 붙어 있어 나중에 한 번에 지울 수 있습니다.

오브젝트 역할
Deployment/Service msa-a Ingress로 들어오는 진입점. 요청을 msa-b로 전달
Deployment/Service msa-b msa-a의 요청을 msa-c로 전달
Deployment/Service msa-c 마지막 단계. 200과 msa-c ok를 응답
ConfigMap msa-a-conf, msa-b-conf, msa-c-conf 각 nginx의 전달 설정. /etc/nginx/conf.d에 마운트
Ingress msa-demo ingressClassName: istio, 호스트 okestro-academy-msa-demo.com → msa-a:80

서비스 포트 이름은 반드시 http로 하고, 파드 라벨에는 app과 version을 넣습니다. Kiali가 이 두 라벨로 앱과 버전을 나눠 그립니다. nginx 전달 설정의 핵심은 다음 한 줄입니다. proxy_http_version 1.1은 Istio 사이드카(Envoy)가 HTTP/1.0 요청을 거부해 426 오류가 나는 것을 막기 위한 설정입니다.

location / { proxy_http_version 1.1; proxy_pass http://msa-b.academy.svc.cluster.local; }

Ingress의 핵심은 다음과 같습니다.

spec:
  ingressClassName: istio
  rules:
  - host: okestro-academy-msa-demo.com
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: msa-a, port: {number: 80}}}}
kubectl apply -f ~/msa-demo.yaml
kubectl -n academy get pod -l demo=kiali-msa

파드의 READY가 2/2(앱 + istio-proxy)이면 사이드카가 붙은 것입니다. 1/1이면 1단계를 다시 확인하고 파드를 재생성합니다.

3. 부하 파드(msa-load)

Kiali는 지난 몇 분 동안 실제로 흐른 요청만 그리므로, 시연 중에는 요청이 계속 흐르도록 부하 파드를 둥니다. Job이나 CronJob이 아니라 Deployment로 만들어야 시작과 중지를 레플리카 수로 간단히 조절할 수 있습니다.

  • 동작: 약 0.5초 간격으로 istio-gateway에 Host: okestro-academy-msa-demo.com 헤더를 단 curl 요청을 보냅니다(약 2 req/s).

  • 사이드카는 붙이지 않습니다. 파드 라벨에 sidecar.istio.io/inject: "false"를 넣습니다. 사이드카가 있으면 그래프 아래에 PassthroughCluster 노드가 생겨 보기에 지저분해집니다. 파드 라벨이 네임스페이스 설정보다 우선합니다.

template:
  metadata:
    labels: {app: msa-load, version: v1, demo: kiali-msa, sidecar.istio.io/inject: "false"}
kubectl apply -f ~/msa-load.yaml
kubectl -n academy get pod -l app=msa-load   # READY 1/1

4. 멀티 파드(msa-b v2)

Ingress → Gateway → Service → 여러 파드 형태를 보여 주기 위해 msa-b-v2 디플로이먼트를 추가합니다. 라벨이 app: msa-b, version: v2이라 기존 msa-b 서비스가 v1과 v2를 함께 선택하고, 요청이 두 버전으로 나뉘어 들어갑니다. msa-b(v1) 디플로이먼트의 셀렉터는 app: msa-b, version: v1로 두어 msa-b-v2와 셀렉터가 겹치지 않게 합니다.

kubectl apply -f ~/msa-b-v2.yaml

5. 동작 확인

도메인 DNS 없이 VIP에 Host 헤더를 직접 넣어 한 번 호출합니다.

curl -s -H "Host: okestro-academy-msa-demo.com" http://192.0.2.67/

msa-c ok가 오면 msa-a → msa-b → msa-c 체인이 정상입니다. 그래프는 요청 후 30~40초 뒤에 나타납니다.

그래프 보는 법

VIOLA의 모니터링 → 트래픽 모니터링에서 네임스페이스는 academy와 istio-system을 함께 선택하고 그래프 유형은 Versioned app graph를 고릅니다. istio-system을 빼면 진입점인 istio-gateway가 보이지 않습니다.

노드와 선의 의미

모양 의미 이번 구성에서
삼각형 Service msa-a, msa-b, msa-c
사각형 앱의 한 버전(워크로드) msa-a v1, msa-b v1, msa-b v2, msa-c v1
박스(A) 버전을 묶은 앱 msa-b 안에 v1과 v2
화살표 라벨 초당 요청 수 등 진입점 약 2 req/s
istio-gateway Ingress의 실제 프록시 요청이 시작되는 지점

파드 하나하나는 노드로 그려지지 않고, 같은 버전의 파드는 하나의 사각형으로 묶입니다. Ingress 오브젝트도 노드가 아니며, 실제 프록시인 istio-gateway가 그 역할을 보여 줍니다. HAProxy는 메시 밖이라 보이지 않습니다.

Display 메뉴와 시간 범위

  • Traffic Animation: 선 위에 점이 흐르게 해 요청이 지나가는 방향을 보여 줍니다.

  • Traffic Rate: 선에 초당 요청 수를 표시합니다.

  • Response Time: 선에 응답 시간(p95 등)을 표시합니다.

  • Traffic Distribution: v1과 v2처럼 갈라지는 선에 분산 비율을 표시합니다.

  • 시간 범위: 시연에는 Last 5m, 새로고침 주기는 Every 10s를 권장합니다.

Display 설정은 화면을 새로 열면 기본값으로 돌아가므로, 시연 직전에 다시 체크해야 합니다.

시연 절차

평소에는 Istio Injection을 끄고 부하 파드도 중지해 두었다가, 시연 직전에 아래 순서로 진행합니다. 주의할 점은 토글을 켜는 것만으로는 기존 파드가 바뀌지 않는다는 것입니다.

  1. VIOLA에서 academy의 Istio Injection을 활성화합니다.

  2. 시험 앱 파드가 사이드카 없이 떠 있다면 재시작해 2/2로 만듭니다.

kubectl -n academy rollout restart deploy msa-a msa-b msa-b-v2 msa-c

  1. 부하 파드를 켭니다. 1/1이면 정상입니다.

kubectl -n academy scale deploy msa-load --replicas=1

  1. 트래픽 모니터링 화면을 열고 네임스페이스(academy, istio-system), 그래프 유형(Versioned app graph), 시간 범위(Last 5m)를 맞춥니다.

  2. Display에서 Traffic Animation, Traffic Rate, Response Time을 체크합니다.

  3. 요청 후 30~40초가 지나면 istio-gateway → msa-a → msa-b(v1, v2) → msa-c가 나타납니다.

  4. 포인트는 세 가지입니다: 요청이 어느 서비스를 지나는지, msa-b가 v1과 v2 두 파드로 나뉘어 들어가는지, 각 구간의 초당 요청 수와 응답 시간과 오류율이 어떤지입니다.

부하 파드 없이 짧게 보여 주려면 Mac에서 bash msa_demo_traffic.sh 5 180처럼 스크립트로 VIP에 초당 5회, 180초 동안 요청을 보낼 수도 있습니다. 또 시연이 끝나면 부하 파드를 0으로 내리고, 시간 범위가 지나면 그래프는 Empty Graph로 돌아갑니다.

트러블슈팅

이번 구성에서 실제로 만났거나 미리 점검한 현상입니다.

현상 원인 조치
파드가 ImagePullBackOff 노드에 외부 인터넷이 없고 AlwaysPullImages로 매번 레지스트리에서 받음 사내 Harbor의 이미지 주소를 정확히 지정
파드가 1/1 (사이드카 없음) 파드가 Istio Injection 활성화 전에 만들어짐 활성화 후 rollout restart로 재생성
그래프에 아무것도 없음(Empty Graph) 선택한 시간 범위에 요청이 없음 부하 파드를 다시 켜고 30~40초 대기, 시간 범위를 늘림
Traffic Animation이 없어짐 화면을 새로 열면 Display 설정이 초기화됨 Display에서 다시 체크
PassthroughCluster 노드가 보임 사이드카가 있는 부하 파드가 게이트웨이를 알려진 서비스로 매칭하지 못했음(정확한 원인은 미확인) 부하 파드에 sidecar.istio.io/inject: "false"
Missing Sidecar 표시 부하 파드에 일부러 사이드카를 붙이지 않았음 오류가 아니므로 그대로 둥니다
증상이 같은 도메인이 404 같은 호스트의 Ingress가 중복됨 호스트를 하나만 남김
서비스에 다른 파드가 섞임 서로 다른 디플로이먼트가 같은 selector를 공유 시험 앱의 app, version 라벨을 고유하게 유지

PassthroughCluster는 메시에 등록되지 않은 목적지로 나가는 트래픽을 사이드카가 그대로 통과시킬 때 Kiali가 그리는 가상 노드입니다. 요청 자체는 정상으로 전달되었습니다.

정리 및 원복

시연이 끝나면 단계별로 되돌립니다.

  1. 트래픽만 멈추기: 부하 파드를 0으로 내립니다. 시험 앱은 남아 있어 다음 시연에 바로 쓸 수 있습니다.

kubectl -n academy scale deploy msa-load --replicas=0

  1. 시험 앱 전체 삭제: demo=kiali-msa 라벨이 붙은 Ingress, Deployment, Service, ConfigMap을 한 번에 지웁니다.

kubectl -n academy delete ingress,deploy,svc,cm -l demo=kiali-msa

  1. Istio Injection 끄기: VIOLA의 네임스페이스 관리에서 academy의 Istio Injection을 비활성화합니다. 이미 사이드카가 붙은 파드는 그대로 남아 있으므로, 시험 앱을 삭제하지 않았다면 파드를 재생성해야 사이드카가 빠집니다.

삭제 후 아래 명령으로 남은 오브젝트가 없는지 확인합니다.

kubectl -n academy get all,ingress,cm -l demo=kiali-msa
