VIOLA 3.0.6 · 워크로드

Deployment 기본 용량 설정 가이드

academy, handson 네임스페이스에서 만드는 Deployment에 CPU·메모리 기본값(requests/limits)이 자동으로 들어가게 하는 방법과, 포털에서 그 값이 적용되도록 Deployment를 만드는 순서입니다. (2026-11-03 · @김윤형)

1. 한눈에 보기

  • 네임스페이스에 LimitRange를 만들어 두면, 파드에 resources가 비어 있을 때 기본값이 자동으로 채워집니다.
  • VIOLA 포털에는 LimitRange를 만드는 메뉴가 없습니다. 클러스터 관리자가 kubectl로 한 번 만들어 둡니다.
  • 포털 기본 모드 폼은 requests.cpu 250m, requests.memory 64Mi, limits.cpu 500m, limits.memory 128Mi를 항상 직접 채워 보냅니다. 네임스페이스를 바꿔도 이 값은 바뀌지 않으므로 LimitRange가 적용되지 않습니다.
  • LimitRange 기본값을 쓰려면 포털 고급 모드(YAML) 에서 resources: 블록을 지우고 만듭니다. (4장)
네임스페이스 LimitRange ResourceQuota 상태
handson handson-defaults (2026-11-02 생성) handson-quota (pods 80, requests CPU 2 / 메모리 4Gi) 이미 있음
academy 없음 없음 3장에서 새로 만듦

2. 기본값 정하기

handson에 이미 적용된 값은 아래와 같고, 이 값으로 동작을 확인했습니다.

구분 CPU 메모리
기본 requests (defaultRequest) 20m 32Mi
기본 limits (default) 200m 128Mi
  • nginx 위주 실습이라 이 정도로 작게 잡았습니다. nginx는 대기 중 CPU 약 1m, 메모리 약 3~8Mi를 씁니다.
  • requests는 스케줄링과 HPA 사용률 계산의 기준이고, limits는 상한입니다. 메모리 limits를 너무 낮추면 접속이 몰릴 때 OOMKilled가 날 수 있어 128Mi 이상을 권합니다.
  • HPA 사용률은 requests.cpu 대비 비율입니다. 기본 requests를 작게 잡을수록 같은 부하에서 사용률이 크게 나옵니다. (예: 50m 기준 loader 1개 약 4.75%p → 10m이면 약 24%p)

참고 값을 바꾸고 싶으면 3장 YAML의 숫자만 고치면 됩니다. handson의 handson-defaults도 바꾸려면 같은 방식으로 kubectl apply를 다시 합니다.

3. 관리자: LimitRange 만들기 (한 번만)

클러스터 노드(예: biz-3)에 root로 접속해서 실행합니다. 쓰기 명령이므로 관리자가 직접 실행합니다.

3.1 현재 상태 확인 (읽기 전용)

kubectl get limitrange,resourcequota -n academy
kubectl get limitrange,resourcequota -n handson

academy에는 No resources found, handson에는 limitrange/handson-defaults와 resourcequota/handson-quota가 나와야 합니다.

3.2 academy용 파일 만들기

cat > limitrange-academy.yaml <<'EOF'
apiVersion: v1
kind: LimitRange
metadata:
  name: academy-defaults
  namespace: academy
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 20m
      memory: 32Mi
    default:
      cpu: 200m
      memory: 128Mi
EOF

3.3 검증 후 적용

서버에 저장하지 않고 먼저 검증합니다.

kubectl apply --dry-run=server -f limitrange-academy.yaml

limitrange/academy-defaults created (server dry run)이 나오면 적용합니다.

kubectl apply -f limitrange-academy.yaml

3.4 적용 확인

kubectl describe limitrange academy-defaults -n academy

CPU 20m/200m, 메모리 32Mi/128Mi가 표에 나오면 됩니다.

참고 LimitRange는 이후에 만들어지는 파드부터 적용됩니다. 이미 떠 있는 파드는 바뀌지 않습니다. 되돌리려면 kubectl delete limitrange academy-defaults -n academy를 실행합니다.

4. 포털에서 기본값이 적용되게 Deployment 만들기

4.1 기본 모드는 값이 고정되어 있습니다

컨테이너 관리 → 디플로이먼트 → 생성의 기본 모드 화면입니다. 리소스 스펙에 값이 이미 채워져 있고, 네임스페이스를 handson으로 바꿔도 그대로입니다.

이 폼으로 만들면 Deployment에 위 값이 그대로 들어가므로 LimitRange는 쓰이지 않습니다.

4.2 고급 모드에서 resources: 블록 지우기

  1. 모드 선택에서 고급 모드를 고릅니다.
  2. YAML의 metadata.name, metadata.namespace(academy 또는 handson), labels, selector, template.metadata.labels의 app 값을 채웁니다.
  3. 기본 템플릿에도 resources:가 들어 있습니다. 아래 그림의 24~30번 줄 7줄 전체를 지웁니다.

지울 부분입니다.

        resources:          # 24번 줄 (여기부터)
          requests:
            cpu: 250m
            memory: 64Mi
          limits:
            cpu: 500m
            memory: 128Mi   # 30번 줄 (여기까지)

주의 resources:만 지우고 requests: 이하를 남기면 들여쓰기가 어긋나 유효성 검사에서 오류가 납니다. 7줄을 모두 지우고, 바로 위 env: []와 바로 아래 imagePullSecrets: [] 줄은 그대로 둡니다.

4.3 최소 YAML 예시

아래처럼 resources:가 없는 YAML이면 됩니다. (replicas는 필요에 맞게 조정, 예: 3)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lr-demo
  namespace: handson
  labels:
    app: lr-demo
spec:
  selector:
    matchLabels:
      app: lr-demo
  replicas: 1
  template:
    metadata:
      labels:
        app: lr-demo
    spec:
      containers:
        - name: nginx
          image: edu-harbor.example.com/library/nginx:latest
          ports:
            - containerPort: 80
              protocol: TCP

4.4 유효성 검사와 생성

  1. YAML 유효성 검사를 눌러 초록색 The requested YAML can be created.가 나오는지 확인합니다.
  2. 생성을 누르고, 확인 창에서 생성을 한 번 더 누릅니다.

5. 적용 여부 확인하기

5.1 파드 상세의 리소스 제한

컨테이너 관리 → 디플로이먼트 → lr-demo → 파드(lr-demo-…) 를 엽니다. 컨테이너 표의 리소스 제한에 cpu: 200 m, memory: 128 Mi가 보이면 LimitRange의 기본 limits가 적용된 것입니다.

참고 배포 상세(Deployment)의 컨테이너 표는 리소스가 -로 보입니다. 값은 Deployment가 아니라 파드에 채워지기 때문이며, 정상입니다.

5.2 파드 YAML의 LimitRanger 표시

파드 상세의 YAML 탭 위쪽 annotations에 아래 문구가 있으면 requests와 limits가 LimitRange로 채워진 것입니다.

kubernetes.io/limit-ranger: "LimitRanger plugin set: cpu, memory request for container nginx; cpu, memory limit for container nginx"

5.3 터미널로 확인 (선택, 읽기 전용)

kubectl get pod -n handson -l app=lr-demo -o jsonpath='{.items[0].spec.containers[0].resources}'

requests에 cpu 20m, memory 32Mi, limits에 cpu 200m, memory 128Mi가 나오면 정상입니다.

6. 알아 둘 점

  • 기본 모드는 적용되지 않습니다. 기본값을 쓰게 하려면 수강생에게 “고급 모드에서 resources: 7줄을 지운다”고 안내해야 합니다.
  • 쿼터: handson-quota는 requests 합계를 제한합니다(CPU 2, 메모리 4Gi, pods 80). 기본 requests 20m/32Mi이면 CPU로는 100개, 메모리로는 128개까지 가능하고 실제 한계는 pods 80입니다. Deployment당 파드 3개면 약 26개 배포까지 만들 수 있습니다. 기본 모드 값(250m)으로 만들면 CPU 쿼터로는 8개 정도에서 한계에 닿습니다.
  • HPA 시연: HPA는 requests.cpu 대비 사용률을 계산합니다. 시연용 hpa-web처럼 값을 직접 지정하는 배포는 LimitRange 영향을 받지 않습니다. 수강생이 기본값으로 만든 배포에 HPA를 붙이면 requests 20m 기준으로 사용률이 계산됩니다.
  • Java 등 큰 앱: 메모리 limits 128Mi는 작아서 OOMKilled가 날 수 있습니다. 이런 앱은 resources:를 직접 지정합니다.

7. 시험용 리소스 정리

확인용으로 만든 lr-demo는 포털에서 지웁니다. 컨테이너 관리 → 디플로이먼트에서 lr-demo를 열고 삭제를 눌러, 확인 창의 확인했습니다에 체크한 뒤 삭제를 누릅니다.

부록. 확인 명령 모음 (읽기 전용)

# LimitRange / ResourceQuota 현황
kubectl get limitrange,resourcequota -n academy
kubectl get limitrange,resourcequota -n handson

# LimitRange 상세
kubectl describe limitrange handson-defaults -n handson
kubectl describe limitrange academy-defaults -n academy

# 쿼터 사용량
kubectl describe resourcequota handson-quota -n handson

# 파드별 requests/limits
kubectl get pod -n handson -o custom-columns=NAME:.metadata.name,REQ_CPU:.spec.containers[*].resources.requests.cpu,REQ_MEM:.spec.containers[*].resources.requests.memory,LIM_CPU:.spec.containers[*].resources.limits.cpu,LIM_MEM:.spec.containers[*].resources.limits.memory
