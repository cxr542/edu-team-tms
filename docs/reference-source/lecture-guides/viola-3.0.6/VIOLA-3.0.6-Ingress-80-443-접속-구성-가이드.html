VIOLA 3.0.6 Ingress 80/443 접속 구성 가이드

Oct 28, 2026 · @김윤형

개요

VIOLA 3.0.6(edu306)에서 만든 ingress는 http://도메인(80)으로 바로 접속됩니다. https://도메인(443)은 기존 5개 도메인만 되고, 새 도메인에는 추가 작업이 필요합니다.

배경. VIOLA 3.0.5는 ingress-nginx(NodePort 30080/30443)를 쓰고, 3.0.6은 Istio ingress(istio-gateway 서비스, NodePort 32080/32443)를 씁니다. 3.0.6에는 80/443으로 받는 앞단이 없어 http://도메인:32080로만 접속했습니다.

해결. biz 클러스터 control-plane 노드 3대(biz-1, biz-2, biz-3)에 HAProxy를 두어 80→32080, 443→32443으로 넓기고, keepalived VIP 192.0.2.67로 접속합니다. 이 구성은 2026-10-28에 적용했고, http는 5개 도메인 모두 VIP와 세 노드에서 200을 확인했습니다.

변경 전과 후

변경 전·후 접속 경로 · 노드 앞단에 HAProxy 추가

변경 전에는 Istio 게이트웨이의 NodePort(32080)로만 받아서 포트 번호를 붙여야 했습니다. 변경 후에는 HAProxy가 80/443으로 받아 같은 게이트웨이로 넘기므로, 포트 번호 없이 접속합니다. 도메인 분기는 이전과 같이 Istio가 ingress의 host로 합니다.

현재 구성

세 노드가 같은 HAProxy 설정을 가지고, VIP는 keepalived가 한 대에만 붙여 줍니다. 요청은 도메인 → VIP(192.0.2.67) → HAProxy → Istio 게이트웨이(NodePort) → ingress 규칙 → 서비스 순서로 지나갑니다.

현재 구성 · VIP와 세 노드

노드 IP keepalived priority HAProxy 포트
edu-bf306-biz-1 192.0.2.89 MASTER (VIP 보유) 150 80, 443, 26443
edu-bf306-biz-2 192.0.2.35 BACKUP 100 80, 443, 26443
edu-bf306-biz-3 192.0.2.21 BACKUP 100 80, 443, 26443
포트 역할 목적지
80 HTTP ingress 세 노드의 NodePort 32080 (roundrobin)
443 HTTPS ingress (TLS는 Istio 게이트웨이에서 종료) 세 노드의 NodePort 32443 (roundrobin)
26443 Kubernetes API (biz-api.okestro-k8s.com) 세 노드의 6443 (balance source)

  • VIP 192.0.2.67은 원래 클러스터 API 주소로 쓰이던 값이고, 웹 80/443도 같은 VIP로 받습니다.

  • HAProxy는 TCP(L4) 모드입니다. 도메인 분기는 Istio가 ingress의 host로 합니다.

  • 클러스터는 AlwaysPullImages가 켜져 있어 파드는 항상 레지스트리에서 이미지를 받습니다(사내 Nexus nexus.okestro-k8s.com:55000 사용).

원인 분석

:32080 없이 접속되지 않았던 이유는 3.0.6에 3.0.5의 앞단(80/443을 받는 계층)이 없었기 때문입니다. 두 환경을 비교한 결과입니다.

항목 VIOLA 3.0.5 (edu) VIOLA 3.0.6 (edu306)
Ingress 컨트롤러 ingress-nginx (차트 4.12.1) Istio ingress (Istio 1.29.5)
ingressClassName nginx istio
외부 노출 서비스 ingress-nginx controller, NodePort 30080 / 30443 istio-gateway, NodePort 32080 / 32443
80/443 접속 https://도메인으로 접속됨(80/443을 받는 앞단 구성은 확인하지 못함) 포트 없는 접속 불가, :32080만 접속
ingress마다 생기는 것 nginx 설정 Istio Gateway / VirtualService 자동 생성
https ingress의 TLS 시크릿을 nginx가 읽음 시크릿을 istio-system에서 읽음

해결 방향은 두 가지였습니다. Istio 게이트웨이의 설정을 바꾸지 않고 노드 앞단에 L4 프록시(HAProxy)를 두는 방법, 또는 게이트웨이를 80/443으로 직접 노출하는 방법입니다. 앞단 프록시 방식을 선택한 이유는 이미 노드 3대가 control-plane이고 keepalived VIP를 쓰는 구조라, 클러스터 설정을 건드리지 않고 적용할 수 있었기 때문입니다.

최초 구성 절차 (HAProxy)

세 노드(biz-1, biz-2, biz-3) 모두에서 같은 절차로 진행합니다. 노드에는 HAProxy가 이미 설치돼 있고, 클러스터 API(26443) 프록시가 /etc/haproxy/haproxy.cfg에 들어 있습니다. 이 파일을 통째로 덮어쓰면 API가 끊기므로, 기존 내용을 백업하고 그 뒤에 80/443 블록을 덧붙입니다.

  1. 기존 설정을 확인하고 백업합니다.

sudo cat /etc/haproxy/haproxy.cfg
sudo cp /etc/haproxy/haproxy.cfg ~/haproxy.cfg.orig.bak

  1. 기존 global, defaults, listen k8s-apiserver 블록은 그대로 두고, 아래 블록을 뒤에 붙인 파일을 ~/haproxy.merged로 만듭니다.

frontend http_in
        bind *:80
        default_backend istio_http

frontend https_in
        bind *:443
        default_backend istio_https

backend istio_http
        balance roundrobin
        option tcp-check
        server biz1 192.0.2.89:32080 check
        server biz2 192.0.2.35:32080 check
        server biz3 192.0.2.21:32080 check

backend istio_https
        balance roundrobin
        option tcp-check
        server biz1 192.0.2.89:32443 check
        server biz2 192.0.2.35:32443 check
        server biz3 192.0.2.21:32443 check

  1. 문법을 검사한 뒤 적용하고 reload합니다.

sudo haproxy -c -f ~/haproxy.merged && sudo cp ~/haproxy.merged /etc/haproxy/haproxy.cfg && sudo systemctl reload haproxy

  1. 포트가 열렸는지와 API가 살아 있는지 확인합니다. 26443, 80, 443이 모두 보여야 합니다.

sudo ss -ltnp | grep -E ':(26443|80|443)\s'
sudo kubectl --kubeconfig /etc/kubernetes/admin.conf get nodes

  1. 서비스가 부팅 시 자동 시작되는지 확인합니다(systemctl is-enabled haproxy keepalived). 방화벽(ufw)이 켜져 있으면 80/443을 허용해야 합니다. biz-3은 비활성이었고 biz-1, biz-2는 확인하지 않았습니다.

검증. 다른 PC에서 노드 IP로 직접 확인합니다. hosts 파일이 없어도 되도록 Host 헤더를 지정합니다.

for ip in 192.0.2.67 192.0.2.89 192.0.2.35 192.0.2.21; do
  curl -s -o /dev/null -w "$ip %{http_code}\n" -m 5 -H "Host: <도메인>" http://$ip/
done

새 ingress 추가 절차 (http)

도메인이 늘어도 HAProxy나 인증서를 만질 필요가 없습니다. VIOLA에서 ingress를 만들고, 그 도메인이 IP로 해석되게 하면 끝입니다.

  1. VIOLA → 워크로드 → 네트워크 → 인그레스 → 생성을 엽니다(클러스터 biz).

  2. 아래 표의 값으로 기본 모드에서 입력하고 생성합니다(확인 팝업에서 생성 클릭).

  3. 도메인이 아이피로 해석되도록 사내 DNS에 도메인 → 192.0.2.67(VIP)을 등록합니다. 시험 PC는 hosts 파일에 192.0.2.67 도메인을 추가해도 됩니다.

  4. http://도메인으로 접속해 확인합니다.

항목 값
모드 기본 모드
클러스터 biz
네임스페이스 서비스가 있는 네임스페이스(실습 handson, 테스트 academy)
이름 중복 확인 버튼으로 사용 가능 여부 확인
인그레스 클래스 istio (목록에 하나뿐이었음)
호스트 새 도메인 (기존 ingress와 겹치면 안 됨)
Path /
서비스 네임스페이스의 Service
서비스 포트 Service가 열어 둔 포트(기본값 8080이 채워져 있으니 확인 후 변경, nginx는 보통 80)

같은 호스트를 가진 ingress를 두 개 만들면 Istio가 중복 호스트로 판단해 404가 납니다. 도메인이 기존 ingress와 겹치지 않는지 생성 전에 목록에서 확인합니다.

검증. 이름 해석 없이도 확인할 수 있습니다. 200이 나오면 정상입니다.

curl -s -o /dev/null -w "%{http_code}\n" --resolve <도메인>:80:192.0.2.67 http://<도메인>/

주의사항과 트러블슈팅

이 구성을 만든 과정에서 실제로 겪은 문제입니다. 가장 큰 위험은 첫 행의 HAProxy 설정 덮어쓰기입니다.

증상 원인 해결
kubectl이 biz-api.okestro-k8s.com:26443 connection refused 기존 haproxy.cfg(API 26443 프록시)를 백업 없이 덮어씁음 원본(haproxy.cfg.bak)에 80/443 블록을 덧붙여 세 노드에 적용. 설정 변경 전에 항상 백업
노드 IP로는 되는데 브라우저에서 도메인이 안 열림 Mac /etc/hosts에 같은 도메인이 여러 IP로 중복돼 첫 행이 우선 적용됨 중복 행 제거. hosts 대신 사내 DNS 사용 권장
가끔 403 Service selector(app=nginx-deployment)가 여러 Deployment 파드를 함께 잡고, 그 중 PVC를 마운트한 파드의 웹 루트가 비어 있음 PVC에 index.html 생성. 근본해결은 Deployment마다 selector를 분리
동일 호스트 ingress를 두 개 만들면 404 Istio가 중복 호스트(duplicate host names)로 보고 blackhole 라우트로 처리 중복 ingress 삭제. 생성 전에 목록에서 host 중복 확인
http://도메인:32080은 되는데 80은 안 됨 80을 받는 프록시가 없거나 HAProxy가 내려감 systemctl is-active haproxy, ss -ltnp로 80/443 리스너 확인

운영 중 지켜야 할 것.

  • /etc/haproxy/haproxy.cfg는 클러스터 API와 웹이 같이 쓰는 파일입니다. 프로비저닝 도구나 업그레이드가 이 파일을 다시 써서 80/443이 사라질 수 있으니, 클러스터 작업 전후에 포트를 확인합니다.

  • 세 노드의 HAProxy 설정은 항상 같아야 합니다. VIP가 어느 노드로 넘어가도 동작해야 하기 때문입니다.

  • biz-1이 내려가면 biz-2와 biz-3(priority가 같음) 중 IP가 큰 biz-2가 VIP를 이어받을 것으로 예상하지만 장애 조치는 직접 검증하지 않았습니다.

점검 명령과 미해결 과제

노드에서(SSH, 읽기 전용).

# HAProxy/keepalived 상태, VIP 위치, 포트
hostname; systemctl is-active keepalived haproxy; ip -br a show ens3
sudo ss -ltnp | grep -E ':(26443|80|443)\s'
# keepalived 설정(상태/우선순위)
sudo grep -E 'state|priority|virtual_router_id|unicast_src_ip' /etc/keepalived/keepalived.conf
# 클러스터 API
 sudo kubectl --kubeconfig /etc/kubernetes/admin.conf get nodes

내 PC에서.

# 포트(세 노드 + VIP)
for ip in 192.0.2.67 192.0.2.89 192.0.2.35 192.0.2.21; do for p in 26443 80 443; do nc -z -G 3 $ip $p && echo "$ip:$p open" || echo "$ip:$p CLOSED"; done; done

향후 과제: https 접속 환경 만들기

https://도메인을 안정적으로 쓰려면 인증서 발급을 자동화해야 합니다. 지금은 자체 서명 인증서 1장을 기존 5개 도메인에 수동으로 적용했을 뿐이고, 새 도메인은 http만 됩니다. cert-manager를 설치하려던 시도는 이미지 반입 단계에서 멈췄습니다(아래 시도 결과).

준비사항

절차 A: 수동 (도메인이 적을 때)

  1. 새 도메인을 SAN에 포함한 인증서와 키를 만듭니다(자체 서명 또는 사내 CA).

  2. istio-system에 kubernetes.io/tls 타입 시크릿을 만듭니다. PEM의 줄바꿈이 공백으로 바뀌면 인증서를 읽지 못하니 파일에서 바로 만듭니다. 시크릿 하나를 여러 도메인이 공유하면 교체 실수가 전체에 영향을 주므로 도메인마다 별도 시크릿을 권장합니다.

  3. VIOLA에서 ingress 상세 → 수정 → YAML에 spec.tls를 추가하고 "YAML 구문 검사" 후 수정합니다.

spec:
  ingressClassName: istio
  tls:
  - hosts: [도메인]
    secretName: 시크릿이름

  1. 검증합니다. curl -k로 200이 나오고, openssl s_client로 SAN에 도메인이 있는지 봅니다.

절차 B: cert-manager (도메인이 계속 늘어날 때)

  1. 외부 망 PC에서 차트(jetstack/cert-manager)와 이미지 4개(controller, webhook, cainjector, startupapicheck)를 linux/amd64로 받습니다. 2026-10-28에는 v1.21.3을 받았습니다(차트는 Kubernetes 1.22 이상을 요구하여 이 클러스터 v1.31에 맞습니다).

  2. 이미지를 Nexus에 올립니다. 노드에서 ctr -n k8s.io images tag 후 ctr images push --plain-http --user <계정>을 쓰며, 비밀번호는 프롬프트에 직접 입력합니다.

  3. Nexus 주소를 가리키게 설치합니다.

helm upgrade --install cert-manager ./cert-manager-<버전>.tgz -n cert-manager --create-namespace \
  --set crds.enabled=true \
  --set imageRegistry=nexus.okestro-k8s.com:55000 \
  --set imageNamespace=k8s

  1. ClusterIssuer를 만듭니다(사내 CA 또는 cert-manager가 만드는 사설 CA).

  2. istio-system에 도메인별 Certificate를 만들어 시크릿을 자동 발급하고, ingress의 spec.tls.secretName이 그 시크릿을 가리키게 합니다. ingress 어노테이션으로 자동 발급되는 방식은 시크릿 위치 시험 후에 선택합니다.

  3. 새 도메인을 추가할 때는 5번과 spec.tls 연결만 반복합니다. 인증서 발급과 갱신은 cert-manager가 합니다.
