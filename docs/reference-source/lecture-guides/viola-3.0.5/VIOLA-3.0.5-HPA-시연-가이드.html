VIOLA 3.0.5

HPA 오토스케일링 시연 가이드

msa-load 부하 조절로 msa-a 파드 자동 증설 보여주기

대상 환경VIOLA 3.0.5, biz 클러스터, 네임스페이스 academy
시연 대상Deployment msa-a (HPA: msa-a-hpa), 부하 발생: Deployment msa-load
선행 구성Kiali MSA 트래픽 모니터링 시연 앱(msa-a/b/c, msa-load, Gateway)이 배포되어 있어야 함
부하 조절VIOLA 포털에서 msa-load의 replicas 변경

1. 시연 개요

부하가 늘면 쿠버네티스가 파드를 자동으로 늘리고, 부하가 줄면 다시 줄이는 HPA(Horizontal Pod Autoscaler) 동작을 눈으로 보여주는 시연입니다.

  • 부하 발생: msa-load 파드가 istio-gateway를 통해 msa-a를 반복 호출합니다. 파드 하나당 약 2 req/s이고, 포털에서 replicas를 올리면 부하가 그만큼 늘어납니다.
  • 측정: metrics-server가 msa-a의 nginx 컨테이너 CPU 사용량을 수집하고, HPA가 requests(10m) 대비 사용률을 계산합니다.
  • 조정: 사용률이 목표(30%)를 넘으면 msa-a 파드를 최대 4개까지 늘리고, 내려가면 줄입니다.

2. 구성도

포털에서 msa-load의 replicas를 바꾸면 msa-a로 가는 요청이 달라지고, metrics-server가 측정한 CPU 사용률을 HPA가 목표와 비교해 msa-a의 파드 수를 조정합니다. 파드가 늘고 줄어드는 모습은 포털의 파드 목록과 터미널의 -w 출력으로 보여줍니다.

참고Kiali 그래프는 파드가 아니라 워크로드(Deployment) 단위로 노드를 그립니다. 파드가 늘어도 msa-a 노드는 하나로 보이고 요청 수(RPS)만 올라가므로, 파드 증감은 Kiali가 아닌 포털과 터미널로 보여줍니다.

3. 사전 준비

3.1 HPA 구성 (msa-a-hpa)

항목값
대상Deployment msa-a (academy)
레플리카최소 1, 최대 4
메트릭ContainerResource, 컨테이너 nginx, CPU 사용률(Utilization) 30%
스케일 업대기 0초, 15초마다 최대 2개 증설
스케일 다운대기 60초 (기본 300초를 시연용으로 단축)
왜 ContainerResource인가msa-a 파드에는 nginx 외에 istio-proxy 사이드카가 있습니다. 기본 Resource 메트릭은 파드 안 모든 컨테이너를 합산해 사용률이 희석될 수 있어, nginx 컨테이너만 기준으로 삼았습니다. 포털의 기본 모드에는 이 유형이 없어(Resource, Pods, Object, External만 제공) 고급 모드(YAML)로 만들었습니다.

3.2 포털에서 HPA 만들기 (이미 만들어진 경우 생략)

  • 워크플로우 > 워크로드 > 오토스케일러 > HPA 탭 > 생성
  • 모드를 "고급 모드"로 선택하고 클러스터 biz를 확인한 뒤 부록 A의 YAML을 입력합니다.
  • "YAML 유효성 검사"에서 생성 가능 메시지를 확인하고 생성합니다.

3.3 시연 직전 점검

순서점검 내용
1msa-a 파드가 1개이고 HPA가 안정(TARGETS가 낮은 값, REPLICAS 1)인지 확인합니다. 이전 시연 직후라면 파드가 줄기까지 1~2분 기다립니다.
2msa-load replicas를 1로 되돌려 둡니다.
3(선택) 확실한 증설을 위해 HPA 목표 사용률을 15% 정도로 낮춥니다. 7장 참고.
4화면을 배치합니다. 3.4 참고.

3.4 화면 구성

  • 포털: 워크플로우 > 워크로드 > 컨테이너 관리에서 msa-a의 파드 목록(또는 msa-a 상세 화면)을 띄웁니다.
  • 터미널 1: HPA 상태 (사용률과 레플리카 수)
kubectl -n academy get hpa msa-a-hpa -w
  • 터미널 2: 파드 생성 과정
kubectl -n academy get pods -l app=msa-a -w

터미널은 biz 클러스터에 접속한 노드(예: biz-2)에서 실행합니다. Kiali는 필요할 때만 열어 요청 수 증가를 한 번 짚는 용도로 씁니다.

4. 시연 순서

단계조작확인 포인트설명 포인트
1현재 상태 보여주기
(터미널 1, 2와 포털 파드 목록)		msa-a 파드 1개, REPLICAS 1, 낮은 사용률평소에는 파드 하나로 충분한 상태
2부하 올리기 (포털)
msa-load 상세 화면의 레플리카 영역에서 + 버튼으로 1 → 8		msa-load 파드 수가 8개로 증가요청이 약 8배(약 16 req/s)로 늘어남
3증설 관찰
(터미널 1, 2와 포털)		15~30초 뒤 TARGETS가 목표(30%) 초과 → REPLICAS 증가 → 새 파드 ContainerCreating → RunningHPA가 사용률을 보고 자동으로 파드 추가
4안정화 관찰파드가 늘면 TARGETS가 다시 내려가 목표 근처에서 안정목표 사용률을 유지하도록 조정하는 것이 HPA의 동작
5부하 내리기 (포털)
msa-load 레플리카 영역에서 − 버튼으로 8 → 1		msa-load 파드 수 감소요청이 다시 줄어듦
6축소 관찰약 1분 뒤 REPLICAS 감소, 파드 Terminating 후 1개로 복귀부하가 줄면 자원을 반환 (축소 대기 60초)

4.1 포털에서 msa-load replicas 바꾸기

  • 워크플로우 > 워크로드 > 컨테이너 관리에서 디플로이먼트 목록을 열고 msa-load를 선택합니다.
  • 상세 화면의 "레플리카" 영역에서 + 버튼으로 늘리고 − 버튼으로 줄입니다. 0 아래로는 내릴 수 없다는 안내가 표시됩니다.
  • 같은 화면 아래 "파드" 목록에서 msa-load 파드가 늘고 줄어드는 것을 바로 확인할 수 있습니다.
참고부하를 아예 멈추려면 replicas를 0으로 두는 대신 1로 두는 편이 안전합니다. 포털에서 0으로 내릴 수 없는 경우에는 터미널에서 kubectl -n academy scale deploy msa-load --replicas=0 을 사용합니다.

5. 시연 중 관찰 예시

리허설에서 관찰한 값입니다. 환경에 따라 달라질 수 있습니다.

시점관찰 결과
msa-load 1개, msa-a 파드 1개nginx CPU 사용률이 오르며 0% → 10% → 30% → 40%/30%
목표 초과 후 약 15초REPLICAS 1 → 2, 이벤트 SuccessfulRescale (cpu container resource utilization above target)
파드 2개 안정 후사용률 40% → 30% → 20%로 내려가 목표 아래에서 유지, 추가 증설 없음

6. 시연 후 정리

  • msa-load replicas를 1로 되돌립니다(포털 − 버튼).
  • msa-a 파드가 1개로 줄어드는 것을 확인합니다(약 1분).
  • HPA를 삭제하려면 포털 오토스케일러 목록에서 msa-a-hpa를 삭제하거나 아래 명령을 사용합니다.
kubectl -n academy delete hpa msa-a-hpa

7. 증설을 더 빠르게, 더 크게 만들려면

HPA는 "필요한 파드 수 = 현재 파드 수 × 현재 사용률 ÷ 목표 사용률"(올림)로 계산합니다.

방법효과비고
msa-load replicas 늘리기파드당 사용량 증가 → 사용률 상승포털 + 버튼. 가장 간단하고 원복도 쉬움
HPA 목표 사용률 낮추기 (30% → 15%)같은 부하에서 더 많은 파드로 증설파드를 건드리지 않아 안전
스케일 업 정책 조정증설 속도(15초당 파드 수) 상향필요한 만큼만 증설되므로 보조적 효과
nginx requests.cpu 낮추기같은 사용량이 더 높은 사용률로 계산됨비권장: Deployment 롤아웃으로 파드가 재시작됨

목표 사용률은 포털 오토스케일러 목록에서 msa-a-hpa를 수정하거나, 터미널에서 아래 명령으로 15%로 바꿀 수 있습니다.

kubectl -n academy patch hpa msa-a-hpa --type=json -p='[{"op":"replace","path":"/spec/metrics/0/containerResource/target/averageUtilization","value":15}]'

반응 속도는 HPA의 지표 확인 주기(기본 15초)와 새 파드가 뜨는 시간(이미지 풀, 사이드카 준비에 수십 초)에 영향을 받습니다. 최대 레플리카(4)를 넘어서는 증설은 일어나지 않습니다.

8. 트러블슈팅

증상원인과 조치
TARGETS가 <unknown>metrics-server 확인(kubectl top pods -n academy가 값을 반환하는지). 대상 컨테이너(nginx)에 requests.cpu가 있는지 확인. 지표 수집까지 1~2분 걸릴 수 있음
사용률이 올라도 파드가 안 늘어남목표 대비 10% 이내 차이는 HPA 허용 오차 안이라 증설하지 않음. 목표를 낮추거나 부하를 더 올림. 이벤트와 Conditions 확인: kubectl -n academy describe hpa msa-a-hpa
새 파드가 Pending노드 리소스 부족. kubectl -n academy get events에서 Insufficient cpu/memory 확인. 3.0.5 academy에는 다른 파드도 있으므로 부하를 과도하게 올리지 않음
파드가 늘었는데 Kiali 그래프에 안 보임정상. Kiali 그래프는 워크로드 단위라 파드 수가 표시되지 않음. 포털 파드 목록과 터미널로 확인
부하를 내려도 파드가 바로 안 줄어듦축소 대기 60초 + 파드 종료 시간이 필요. 1~2분 기다림
새 파드 시작 시 Startup probe failed 경고istio-proxy가 준비되는 순간의 일시적 경고로 정상

부록 A. HPA 매니페스트 (msa-a-hpa)

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: msa-a-hpa, namespace: academy, labels: {demo: kiali-msa}}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: msa-a}
  minReplicas: 1
  maxReplicas: 4
  metrics:
  - type: ContainerResource
    containerResource:
      name: cpu
      container: nginx
      target: {type: Utilization, averageUtilization: 30}
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies: [{type: Pods, value: 2, periodSeconds: 15}]
    scaleDown:
      stabilizationWindowSeconds: 60
입력 팁포털 고급 모드의 YAML 편집기는 자동 들여쓰기가 적용되어 여러 줄을 그대로 입력하면 들여쓰기가 어긋날 수 있습니다. 붙여 넣기가 가능하면 그대로 붙여 넣고, 직접 입력할 때는 한 줄 JSON 형태로 입력해도 YAML로 처리됩니다.

부록 B. 확인 명령 모음

# HPA 상태 (사용률/레플리카)
kubectl -n academy get hpa msa-a-hpa -w

# msa-a 파드 생성/삭제 과정
kubectl -n academy get pods -l app=msa-a -w

# nginx 컨테이너 사용량
kubectl -n academy top pod -l app=msa-a --containers

# HPA 상세 (이벤트, 조건)
kubectl -n academy describe hpa msa-a-hpa

# 부하 파드 수 (포털 대신 터미널로 조절할 때)
kubectl -n academy scale deploy msa-load --replicas=8
kubectl -n academy scale deploy msa-load --replicas=1
